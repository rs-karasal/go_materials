# 13. Ошибки как значения: `error`, `errors.Is` и `errors.As`

> ⏱ **~50 минут** · теория 20 мин · практика 30 мин

Обработка ошибок — то, за что Go чаще всего критикуют, и то, что определяет его характер сильнее всего остального. Здесь нет исключений: ошибка — обычное значение, которое возвращают, проверяют и передают дальше. Разберём, как это работает и как не превратить код в свалку однотипных проверок.

## `error` — обычный интерфейс

```go
type error interface {
	Error() string
}
```

Всё. Любой тип с методом `Error() string` является ошибкой.

Идиома возврата знакома с пятой статьи:

```go
if err := doSomething(); err != nil {
	return err
}
```

`nil` означает «всё в порядке». Проверка `err != nil` — самая частая строка в коде на Go.

Почему так, а не исключения? Три причины, которые стоит понимать.

**Ошибка видна в сигнатуре.** `func Open(name string) (*File, error)` сразу сообщает, что вызов может не удаться. С исключениями это приходится узнавать из документации.

**Нет невидимых путей выхода.** В языке с исключениями любая строка может прервать функцию. В Go выход только через явный `return`, и код читается сверху вниз.

**Ошибку трудно проигнорировать молча.** Компилятор не даст объявить `err` и не использовать его.

Цена — многословность. Три вызова подряд дают девять строк проверок. С этим живут, и через неделю глаз перестаёт их замечать.

## Создание ошибок

Два способа:

```go
errors.New("запись не найдена")
fmt.Errorf("поиск записи %d: %w", id, ErrNotFound)
```

`errors.New` — для простого текста. `fmt.Errorf` — когда нужна подстановка значений.

**Сообщения об ошибках в Go пишут с маленькой буквы и без точки в конце.** Причина в том, что они склеиваются: `чтение конфигурации: open config.toml: no such file or directory`. Заглавные буквы посреди такой цепочки выглядели бы странно.

## Сторожевые ошибки

Когда вызывающему коду нужно **различать** причины сбоя, заводят переменную пакета:

```go
var ErrNotFound = errors.New("запись не найдена")
```

Имя начинается с `Err`, объявляется на уровне пакета. Таковы `sql.ErrNoRows`, `io.EOF`, `os.ErrNotExist` — с ними вы будете сталкиваться постоянно.

## Оборачивание и `errors.Is`

Просто вернуть ошибку наверх — значит потерять контекст: «no such file or directory» не говорит, какой файл и зачем открывали. Поэтому ошибку **оборачивают**, добавляя слой:

```go
return fmt.Errorf("поиск записи %d: %w", id, ErrNotFound)
```

Глагол `%w` (от *wrap*) — не то же, что `%v`. Он сохраняет исходную ошибку внутри, позволяя добраться до неё позже.

```
текст: поиск записи 200: запись не найдена
```

Теперь важное. Прямое сравнение обёрнутой ошибки не сработает:

```go
err == ErrNotFound      // false
errors.Is(err, ErrNotFound)   // true
```

`errors.Is` разворачивает цепочку и сравнивает на каждом уровне. **Всегда используйте её вместо `==`** — иначе достаточно одному промежуточному слою обернуть ошибку, и ваша проверка молча перестанет работать.

Это касается и стандартной библиотеки:

```go
err = fmt.Errorf("чтение конфигурации: %w", err)
errors.Is(err, os.ErrNotExist)     // true
```

Правило оборачивания: **добавляйте контекст на каждом уровне, но не дублируйте**. Плохо: `не удалось прочитать файл: ошибка чтения файла: ...`. Хорошо, когда каждый слой добавляет свою деталь — что делали и с чем.

## Свои типы ошибок и `errors.As`

Когда ошибка должна нести **данные**, а не только текст, объявляют тип:

```go
type ValidationError struct {
	Field string
	Msg   string
}

func (e *ValidationError) Error() string {
	return fmt.Sprintf("поле %q: %s", e.Field, e.Msg)
}
```

Метод объявляют на указателе — это соглашение: так две ошибки с одинаковыми полями остаются разными значениями.

Достают такую ошибку из цепочки через `errors.As`:

```go
var ve *ValidationError
if errors.As(err, &ve) {
	fmt.Printf("поле=%s\n", ve.Field)
}
```

`As` ищет в цепочке ошибку нужного типа и записывает её в переданную переменную — обязательно по указателю.

Разница проста: **`Is` — про конкретное значение, `As` — про тип**. Хотите узнать «это именно ErrNotFound?» — `Is`. Хотите достать поля — `As`.

## Несколько ошибок сразу

Иногда нужно вернуть все ошибки, а не первую, — например, при валидации формы:

```go
both := errors.Join(e1, e2)
errors.Is(both, e1)     // true
errors.Is(both, e2)     // true
```

`errors.Join` (Go 1.20) объединяет ошибки; текст печатается по строке на каждую, а `Is` находит любую из них.

## Типичные ошибки при работе с ошибками

**Игнорирование через `_`.** `data, _ := os.ReadFile(path)` — код, который «работает», пока файл существует. Если ошибка действительно не важна, напишите комментарий почему.

**Логирование и возврат одновременно.** `log.Println(err); return err` приводит к тому, что одна ошибка попадает в лог пять раз по пути наверх. Правило: **либо обработали, либо вернули**. Логирует тот, кто принимает решение, — обычно верхний уровень.

**Потеря `%w`.** `fmt.Errorf("контекст: %v", err)` превращает ошибку в текст, и `errors.Is` перестаёт работать. Пишите `%w`, если нет причины скрывать исходную ошибку намеренно.

**Проверка по тексту.** `if strings.Contains(err.Error(), "not found")` — хрупко: текст меняется. Для этого и существуют `Is` и `As`.

## Что запомнить

- `error` — интерфейс с одним методом `Error() string`; `nil` означает успех.
- Ошибки — значения: они видны в сигнатуре, не создают невидимых путей выхода и не игнорируются молча.
- Сообщения пишут с маленькой буквы и без точки — они склеиваются в цепочку.
- Сторожевые ошибки (`ErrNotFound`) объявляют переменной пакета для различения причин.
- `%w` в `fmt.Errorf` оборачивает ошибку, сохраняя исходную внутри.
- Сравнивайте через `errors.Is`, а не `==`: обёртка ломает прямое сравнение.
- `errors.Is` — про значение, `errors.As` — про тип и доступ к полям.
- `errors.Join` объединяет несколько ошибок.
- Не логируйте и не возвращайте ошибку одновременно; не проверяйте ошибки по тексту.

## Практика

**1. Первая ошибка.** Напишите функцию деления, возвращающую ошибку при нулевом делителе. Обработайте оба случая. Готово, когда программа не паникует.

**2. Сторожевая ошибка.** Заведите `ErrEmptyInput` и функцию, возвращающую её. Оберните результат в вызывающей функции через `%w` и проверьте `errors.Is` на верхнем уровне. Затем замените `%w` на `%v` и посмотрите, что сломается. Готово, когда разница ясна.

**3. Свой тип ошибки.** Опишите `ValidationError` с полями «поле» и «причина». Напишите валидатор формы, возвращающий такую ошибку, и вызывающий код, который через `errors.As` печатает имя проблемного поля. Готово, когда имя поля извлечено, а не выпарсено из текста.

**4. Цепочка контекста.** Постройте цепочку из трёх уровней: чтение файла → разбор конфигурации → запуск приложения, оборачивая ошибку на каждом. Готово, когда финальное сообщение читается как рассказ и `errors.Is` находит исходную ошибку `os.ErrNotExist`.

**5. Несколько ошибок.** Напишите валидатор, проверяющий три поля и возвращающий через `errors.Join` все нарушения сразу. Готово, когда `errors.Is` находит каждое из них по отдельности.
