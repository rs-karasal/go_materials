# 14. `panic`, `recover` и когда они уместны

> ⏱ **~40 минут** · теория 15 мин · практика 25 мин

`panic` выглядит как исключение, и новички из Java или Python сразу пытаются использовать его для обработки ошибок. Это главная ошибка, которую нужно пресечь на старте: паника в Go — не альтернатива `error`, а способ сказать «программа в состоянии, в котором продолжать нельзя».

## Что делает `panic`

Останавливает нормальное выполнение, разматывает стек, выполняя все отложенные вызовы, и завершает программу с ненулевым кодом:

```
panic: assignment to entry in nil map

goroutine 1 [running]:
main.main()
	/path/main.go:5 +0x34
exit status 2
```

Рантайм паникует сам при нарушении инвариантов: выход за границы слайса, разыменование `nil`-указателя, запись в `nil`-карту, деление на ноль. Вызвать её вручную можно через `panic(значение)` — аргументом бывает что угодно, обычно строка или ошибка.

Важно: `defer` при панике **выполняется**. Именно поэтому освобождение ресурсов через `defer` из статьи 5 надёжно даже в аварийных ситуациях:

```go
func nested() {
	defer fmt.Println("defer выполнился даже при панике")
	panic("глубокая паника")
}
```

## Когда паниковать уместно

Критерий: **паника означает ошибку программиста, а не ситуацию среды**. Файл не найден, сеть недоступна, пользователь ввёл ерунду — это `error`. Нарушение внутреннего инварианта — паника.

Три законных случая:

**1. Невозможное состояние.** Значение, которого по построению быть не может:

```go
switch status {
case Active, Blocked:
	// ...
default:
	panic(fmt.Sprintf("неизвестный статус: %d", status))
}
```

**2. Функции `Must...`.** Соглашение: `MustCompile`, `MustLoad` паникуют вместо возврата ошибки, потому что вызываются на этапе инициализации с заведомо корректными данными:

```go
func MustLoad(port int) *Config {
	if port <= 0 {
		panic("некорректный порт")
	}
	return &Config{Port: port}
}

var re = regexp.MustCompile(`^\d+$`)     // из стандартной библиотеки
```

Логика проста: если регулярное выражение, написанное прямо в коде, не компилируется — это баг, и падать надо сразу при старте, а не через месяц в проде.

**3. Инициализация, без которой работать нельзя.** Не удалось подключиться к базе на старте сервиса — падайте, а не запускайтесь наполовину.

Во всех остальных случаях — `error`. Особенно **не паникуйте в библиотечном коде**: вы отбираете у пользователя право решать, что делать с проблемой.

## `recover`

Перехватывает панику и возвращает переданное в неё значение. Работает **только внутри `defer`**:

```go
func safeDivide(a, b int) (result int, err error) {
	defer func() {
		if r := recover(); r != nil {
			err = fmt.Errorf("восстановлено после паники: %v", r)
		}
	}()
	return a / b, nil
}
```

```
5 <nil>
0 восстановлено после паники: runtime error: integer divide by zero
```

Разберём механику. `recover()` вне `defer` возвращает `nil` и ничего не делает. Внутри — останавливает разматывание стека, и функция завершается нормально. Именованный результат `err` позволяет отложенной функции подменить возвращаемое значение — приём из статьи 5.

Аргумент паники — `any`, поэтому его обычно разбирают:

```go
if e, ok := r.(error); ok {
	err = fmt.Errorf("паника-ошибка: %w", e)
} else {
	err = fmt.Errorf("паника: %v", r)
}
```

Если паниковали ошибкой, её тип сохраняется, и `errors.Is` продолжает работать.

## Где `recover` действительно нужен

Список короткий:

- **На границе сервера.** HTTP-обработчик не должен ронять весь сервис из-за паники в одном запросе. В `net/http` такая защита встроена, но в своих воркерах её пишут руками.
- **В библиотеке — чтобы не выпускать панику наружу.** Внутренний разбор может паниковать для скорости, но на публичной границе паника превращается в `error`.
- **В тестах и инструментах**, где нужно поймать сбой и продолжить.

Чего делать **не** нужно: заворачивать каждую функцию в `recover` «на всякий случай». Это прячет баги, которые должны быть видны и исправлены.

## Паника в горутине убивает всё

Самое важное практическое следствие:

```go
defer func() {
	if r := recover(); r != nil {
		fmt.Println("не поймаем:", r)
	}
}()
go func() { panic("паника в горутине") }()
```

```
panic: паника в горутине

goroutine 35 [running]:
```

`recover` в `main` **не поймал** панику из горутины: обработчик находится в другом стеке. Непойманная паника в любой горутине завершает всю программу.

Отсюда правило, которое пригодится в шестой части курса: **каждая долгоживущая горутина, выполняющая внешний код, должна иметь собственный `recover`**. Пул воркеров без такой защиты падает целиком из-за одной некорректной задачи.

## Что запомнить

- `panic` разматывает стек, выполняя `defer`, и завершает программу.
- Паника — про ошибку программиста, `error` — про ситуацию среды.
- Законные случаи: невозможное состояние, функции `Must...`, критичная инициализация.
- В библиотечном коде паниковать нельзя — это отбирает выбор у пользователя.
- `recover` работает только внутри `defer` и возвращает аргумент паники.
- Именованный результат позволяет отложенной функции превратить панику в ошибку.
- `recover` нужен на границе сервера, на публичной границе библиотеки и в инструментах — не «на всякий случай».
- `recover` не ловит панику из другой горутины; непойманная паника убивает всю программу.

## Практика

**1. Паника рантайма.** Вызовите три паники без `panic()`: выход за границы слайса, разыменование `nil`-указателя, запись в `nil`-карту. Запишите сообщения. Готово, когда все три воспроизведены.

**2. `defer` при панике.** Напишите функцию с двумя `defer` и паникой между ними. Предскажите, какие сообщения появятся. Готово, когда предсказание подтвердилось.

**3. Паника в ошибку.** Напишите функцию, выполняющую произвольную операцию и возвращающую `error` вместо паники. Проверьте на делении на ноль и на выходе за границы. Готово, когда оба случая вернули ошибку, а не уронили программу.

**4. Функция `Must`.** Напишите `MustParseConfig(s string) Config`, паникующую при некорректном вводе, и её пару `ParseConfig`, возвращающую ошибку. Объясните, когда какая уместна. Готово, когда обе реализованы и вы можете назвать место вызова каждой.

**5. Паника в горутине.** Запустите горутину, которая паникует, и убедитесь, что `recover` в `main` не помогает. Затем добавьте `recover` внутрь самой горутины. Готово, когда программа переживает панику воркера.
