# 11. Интерфейсы и неявная реализация

> ⏱ **~50 минут** · теория 20 мин · практика 30 мин

Интерфейс в Go — набор методов, которые тип обязуется предоставить. Идея знакома по Java и C#, но реализована противоположно: тип **не объявляет**, что реализует интерфейс. Соответствие проверяется автоматически. Из этого решения вырастает весь стиль проектирования на Go.

## Объявление и реализация

```go
type Shape interface {
	Area() float64
	Perimeter() float64
}

type Rect struct{ W, H float64 }

func (r Rect) Area() float64      { return r.W * r.H }
func (r Rect) Perimeter() float64 { return 2 * (r.W + r.H) }
```

Всё. Слова `implements` нет — `Rect` реализует `Shape` просто потому, что имеет нужные методы.

```go
shapes := []Shape{Rect{3, 4}, Circle{1}}
for _, s := range shapes {
	fmt.Println(describe(s))
}
```

```
площадь 12.00, периметр 14.00
площадь 3.14, периметр 6.28
```

Если метода не хватает, компилятор скажет об этом в момент присваивания:

```
ni/main.go:8:12: cannot use T{} as S value: T does not implement S (missing method Area)
```

## Почему неявно

Это не синтаксическая экономия, а другой подход к проектированию.

В Java интерфейс объявляет **автор типа**: чтобы использовать чужой класс со своим интерфейсом, нужно править чужой код или писать обёртку. В Go интерфейс объявляет **потребитель**. Вы описываете, что вам нужно, — и любой подходящий тип, включая написанный до вас и без знания о вас, подойдёт.

Отсюда главная идиома Go: **интерфейс объявляют там, где его используют, а не там, где реализуют**. Пакет, отдающий данные, возвращает конкретный тип; пакет, принимающий их, объявляет у себя минимальный интерфейс с нужными методами.

Второе следствие — **интерфейсы делают маленькими**. Чем меньше методов, тем больше типов подойдёт. Каноничный пример из стандартной библиотеки — один метод:

```go
type Writer interface {
	Write(p []byte) (n int, err error)
}
```

Реализуйте его — и ваш тип примут все функции, умеющие писать:

```go
type Counter struct{ N int }

func (c *Counter) Write(p []byte) (int, error) {
	c.N += len(p)
	return len(p), nil
}

var c Counter
fmt.Fprintf(&c, "привет %s", "мир")
fmt.Println(c.N)      // 19
```

Ваш счётчик встал на место файла или сетевого соединения — без единой строчки, знающей про `fmt`. То же работает с `strings.Builder`, `os.Stdout`, HTTP-ответом.

В сообществе это формулируют так: «чем больше методов в интерфейсе, тем слабее абстракция».

## Получатель и реализация

Тонкость, на которой спотыкаются:

```go
// ❌ не компилируется
func (c *C) Inc() { c.N++ }

var s S = C{}
```

```
pr/main.go:10:12: cannot use C{} as S value: C does not implement S
                  (method Inc has pointer receiver)
```

Правило: если метод объявлен с **получателем-указателем**, интерфейс реализует только `*C`, но не `C`. Обратное не так — методы со значением-получателем доступны и у указателя.

Причина в том, что не всякое значение адресуемо: элемент карты, результат функции. Взять адрес автоматически компилятор не всегда может, поэтому и не разрешает.

Лечится передачей адреса: `var s S = &C{}`. Это ещё один аргумент за правило из прошлой статьи — не смешивать получатели в одном типе.

## Нулевое значение и ловушка `nil`

Нулевое значение интерфейса — `nil`, вызов метода на нём паникует.

А теперь самая известная ловушка Go:

```go
var typed *Rect          // nil-указатель
var iface Shape = typed
fmt.Println(typed == nil, iface == nil)
```

```
указатель nil: true    интерфейс nil: false
```

Интерфейс не равен `nil`, хотя внутри лежит `nil`-указатель. Причина в устройстве: интерфейс — это пара «тип, значение». Здесь тип есть (`*Rect`), значение пусто. Пара с заполненным типом не равна `nil`.

Где это стреляет — в функциях, возвращающих ошибку:

```go
func doWork() error {
	var err *MyError = nil
	// ...
	return err      // вернётся НЕ nil!
}

if err := doWork(); err != nil {
	// сюда попадём всегда
}
```

Правило: **не объявляйте переменную конкретного типа ошибки для возврата**. Возвращайте `nil` буквально или объявляйте переменную типа `error`.

## Комбинирование

Интерфейсы встраиваются друг в друга — так собираются составные из мелких:

```go
type ReadWriter interface {
	Reader
	Writer
}
```

Именно так устроен `io.ReadWriter` в стандартной библиотеке. Приём позволяет держать базовые интерфейсы однометодными, собирая нужные комбинации по месту.

## Что запомнить

- Интерфейс — набор методов; реализация неявная, слова `implements` нет.
- Интерфейс объявляет потребитель, а не автор типа, — поэтому подходят и чужие типы.
- Чем меньше методов, тем полезнее интерфейс; однометодные (`io.Writer`) — идеал.
- Метод с получателем-указателем реализует интерфейс только для `*T`, но не для `T`.
- Нулевое значение интерфейса — `nil`; вызов метода на нём паникует.
- Интерфейс — пара «тип, значение»; `nil`-указатель внутри интерфейса делает его **не** равным `nil`.
- Не возвращайте переменную конкретного типа ошибки — возвращайте `nil` или переменную типа `error`.
- Интерфейсы встраиваются друг в друга.

## Практика

**1. Первый интерфейс.** Опишите `Speaker` с методом `Speak() string`, реализуйте его для двух типов и напишите функцию, принимающую `Speaker`. Готово, когда функция работает с обоими типами без изменений.

**2. Свой `io.Writer`.** Реализуйте тип, который при записи считает строки и подсчитывает количество байт. Передайте его в `fmt.Fprintf`. Готово, когда ваш тип принят стандартной функцией.

**3. Ловушка получателя.** Объявите интерфейс и тип с методом на указателе, попробуйте присвоить значение. Разберите ошибку, затем почините. Готово, когда понимаете, почему компилятор не взял адрес сам.

**4. Ловушка nil.** Воспроизведите случай, когда функция возвращает `nil`-указатель как `error`, и проверка `err != nil` срабатывает ошибочно. Почините. Готово, когда обе версии воспроизведены осознанно.

**5. Интерфейс на стороне потребителя.** Напишите функцию отчёта, которой нужен только метод `Name() string`. Объявите минимальный интерфейс рядом с ней и передайте туда структуру из «чужого» пакета вашего проекта. Готово, когда «чужой» пакет ничего не знает об интерфейсе.
