# 30. Финальный проект и чек-лист Go-джуна

> ⏱ **~8–12 часов** · теория 20 мин · проект 8–12 часов

Двадцать девять статей позади. Осталось собрать знания в одну работающую вещь: отдельные темы забываются, проект — нет. Ниже разбор архитектуры финального задания, чек-лист для самопроверки и ответ на вопрос «что учить дальше».

## Проект: сервис задач

HTTP API для управления задачами с хранением в базе. Задача выбрана не случайно: чтобы её сделать, придётся задействовать почти каждую тему курса.

**Требования:**

- REST API: создание, список с фильтром по статусу, получение по идентификатору, смена статуса, удаление;
- хранение в SQLite (или PostgreSQL) через `database/sql`;
- конфигурация из переменных окружения, структурные логи, graceful shutdown;
- корректные коды ответов и внятные ошибки;
- тесты на бизнес-логику и на обработчики, прогон под `-race`.

## Архитектура

Три слоя с зависимостями в одну сторону: HTTP → сервис → хранилище. Домен не знает ни про HTTP, ни про SQL.

```
tasker/
├── cmd/tasker/main.go        // конфигурация, сборка зависимостей, запуск
├── internal/
│   ├── task/                 // домен: модель, ошибки, бизнес-логика
│   ├── store/                // реализация Repository на database/sql
│   └── httpapi/              // обработчики, маршруты, middleware
└── migrations/
```

Начните с домена — в Go это самый естественный порядок.

```go
type Status int

const (
	Todo Status = iota
	InProgress
	Done
)

func (s Status) String() string {
	switch s {
	case Todo:
		return "todo"
	case InProgress:
		return "in_progress"
	case Done:
		return "done"
	default:
		return fmt.Sprintf("unknown(%d)", int(s))
	}
}
```

Статус — свой тип на основе `int` с `iota` и методом `String()`, а не строка: невозможные состояния становятся непредставимыми, а печать остаётся читаемой.

Дальше — сторожевые ошибки и интерфейс хранилища, **объявленный у потребителя** (статья 11):

```go
var (
	ErrNotFound   = errors.New("задача не найдена")
	ErrEmptyTitle = errors.New("пустое название задачи")
)

type Repository interface {
	Add(ctx context.Context, t Task) (int64, error)
	Get(ctx context.Context, id int64) (Task, error)
	List(ctx context.Context) ([]Task, error)
}
```

Бизнес-логика не знает, откуда берутся данные:

```go
type Service struct {
	repo Repository
	now  func() time.Time
}

func (s *Service) Create(ctx context.Context, title string) (Task, error) {
	if title == "" {
		return Task{}, ErrEmptyTitle
	}
	t := Task{Title: title, Status: Todo, CreatedAt: s.now()}
	id, err := s.repo.Add(ctx, t)
	if err != nil {
		return Task{}, fmt.Errorf("сохранение задачи: %w", err)
	}
	t.ID = id
	return t, nil
}
```

Обратите внимание на поле `now func() time.Time`. Это не усложнение ради красоты: подменив его в тесте на фиксированное время, вы получаете детерминированную проверку `CreatedAt`. Тот же приём применим к генераторам идентификаторов и случайным числам.

В этих тридцати строках собрано полкурса: свой тип с `iota` и `String()`, сторожевые ошибки, интерфейс у потребителя, оборачивание через `%w`, контекст первым параметром.

**Тесты без базы.** Раз хранилище спрятано за интерфейсом, для тестов достаточно реализации в памяти:

```go
type memRepo struct {
	items map[int64]Task
	next  int64
	err   error
}
```

Поле `err` позволяет заставить хранилище сломаться и проверить путь ошибки. Табличный тест из статьи 22 покрывает успех, валидацию и сбой хранилища одним набором случаев — на скелете выше это дало 95% покрытия за три теста.

**Порядок работы:** домен и тесты → хранилище → HTTP → конфигурация и запуск. К моменту, когда дойдёте до обработчиков, логика уже проверена.

## Чек-лист Go-джуна

Отметьте, что можете объяснить и применить без подсказок.

**Основы**

- Понимаю разницу между значением и указателем и знаю, когда брать какой
- Объясняю устройство слайса и почему `append` может испортить исходные данные
- Знаю, чем `nil`-карта отличается от пустой и когда будет паника
- Понимаю, почему `len` строки не равен числу символов

**Типы и абстракции**

- Выбираю получатель метода осознанно и не смешиваю их в одном типе
- Объявляю маленькие интерфейсы на стороне потребителя
- Знаю про ловушку `nil`-интерфейса
- Применяю дженерики там, где они уместнее интерфейса

**Ошибки**

- Оборачиваю ошибки через `%w` и проверяю через `errors.Is` / `errors.As`
- Не логирую и не возвращаю ошибку одновременно
- Понимаю, когда уместна паника, а когда `error`

**Конкурентность**

- Запускаю горутины и корректно дожидаюсь их через `WaitGroup`
- Понимаю, что такое гонка данных, и запускаю тесты под `-race`
- Выбираю между каналом и мьютексом осознанно
- Передаю `context` и умею отменять работу по таймауту
- Знаю, что такое утечка горутин, и умею её находить

**Практика**

- Организую проект по пакетам, понимаю `internal/` и запрет циклов
- Пишу табличные тесты и подменяю зависимости через интерфейсы
- Читаю вывод бенчмарка и знаю, что такое `allocs/op`
- Пишу HTTP-сервис со структурными логами и graceful shutdown
- Работаю с `database/sql`, не теряя соединения
- Держу в CI `gofmt`, `go vet`, `staticcheck` и `go test -race`

Если отмечено больше двух третей — вы джун. Оставшееся честнее добирать на реальных задачах, чем ещё одним прогоном теории.

## Что дальше

**Практика, а не новая теория.** Самая частая ошибка после курса — начать второй учебник. Пишите: свой инструмент, участие в open source, задачи на Exercism или Advent of Code.

**Читайте стандартную библиотеку.** В Go это особенно полезно: её исходники — образец идиоматичного кода, и `Ctrl+клик` в редакторе ведёт прямо в них. Начните с `net/http`, `io`, `errors`.

**Темы за рамками курса** — беритесь по мере надобности:

- **gRPC и Protocol Buffers** — межсервисное взаимодействие.
- **Kafka, NATS, RabbitMQ** — очереди и события.
- **Docker, Kubernetes** — эксплуатация сервисов.
- **OpenTelemetry, Prometheus** — наблюдаемость.
- **Устройство планировщика и сборщика мусора** — глубокая оптимизация.
- **`reflect` и кодогенерация** — библиотеки и фреймворки.
- **`unsafe`, cgo** — связывание с C, низкий уровень.

## Что запомнить

- Проект закрепляет знания лучше, чем повторение теории.
- Зависимости идут в одну сторону: HTTP → сервис → хранилище; домен не знает про транспорт и SQL.
- Интерфейс хранилища объявляют в домене — так тесты обходятся реализацией в памяти.
- Подмена `time.Now` через поле-функцию делает тесты детерминированными.
- Свои типы с `iota` и `String()` делают невозможные состояния непредставимыми.
- Джун — это не «знаю всё», а «читаю ошибки, пишу тесты и довожу задачу до конца».
- Дальше учат не новые главы, а реальные задачи.

## Практика

**1. Домен.** Реализуйте пакет `task`: модель, статусы с `iota` и `String()`, сторожевые ошибки, интерфейс `Repository`, сервис с валидацией. Покройте табличными тестами с хранилищем в памяти. Готово, когда `go test -race -cover` даёт больше 80% и `staticcheck` молчит.

**2. Хранилище.** Реализуйте `Repository` на `database/sql` со схемой в миграции. Готово, когда те же тесты сервиса проходят и с реальной базой, и с памятью.

**3. HTTP.** Добавьте обработчики для всех операций, middleware логирования и восстановления после паники. Правильно отображайте доменные ошибки в коды: `ErrNotFound` → 404, `ErrEmptyTitle` → 400. Готово, когда все коды корректны и проверены через `httptest`.

**4. Эксплуатация.** Добавьте конфигурацию из окружения, структурные логи с `request_id` и graceful shutdown. Готово, когда сервис переживает `SIGTERM`, не обрывая запрос в работе.

**5. Расширение (по желанию).** Выберите одно: пагинация и фильтры в списке; фоновый воркер, архивирующий старые задачи по тикеру; аутентификация по токену; выгрузка отчёта с параллельной обработкой через `errgroup`. Готово, когда домен не изменился — только слой вокруг него.
