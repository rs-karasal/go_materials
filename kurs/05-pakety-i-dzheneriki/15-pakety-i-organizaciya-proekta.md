# 15. Пакеты, экспорт и организация проекта

> ⏱ **~45 минут** · теория 20 мин · практика 25 мин

Модуль из статьи 2 — единица распространения, пакет — единица организации кода внутри него. Правила здесь простые, но в них есть несколько жёстких ограничений, о которых лучше узнать до того, как проект разросся: запрет циклических импортов и особая папка `internal`.

## Пакет

Пакет — это **папка**. Все файлы в ней объявляют одно имя в первой строке:

```go
// Package money содержит операции с денежными суммами.
package money
```

Имя пакета обычно совпадает с именем папки. Правила именования:

- одно слово, в нижнем регистре, без подчёркиваний: `store`, `httputil`;
- **никаких `utils`, `helpers`, `common`** — такие пакеты растут бесконечно и ни о чём не говорят;
- имя пакета — часть имени функции при вызове, поэтому не дублируйте его: `http.Server`, а не `http.HTTPServer`.

Комментарий над `package` — документация пакета. Он начинается со слов «Package имя …» и попадает в `go doc`.

## Экспорт

Правило вы знаете с первой статьи: **заглавная буква — экспортировано, строчная — нет**.

```go
type Amount int64          // видно снаружи
func New(...) Amount       // видно
var defaultCurrency = ...  // не видно
```

Работает для всего: типов, функций, методов, полей структур, констант. Никаких модификаторов доступа в языке нет.

Приватность действует **на уровне пакета**, а не типа: функция может обращаться к неэкспортированным полям любой структуры своего пакета. Это заметно отличается от Java, где `private` ограничивает доступ классом.

Следствие: держите в пакете то, что действительно связано. Пакет — это граница инкапсуляции.

## Импорты

Путь импорта — это **имя модуля плюс путь папки**:

```go
import (
	"fmt"

	"github.com/example/shop/internal/store"
	"github.com/example/shop/pkg/money"
)
```

Стандартная библиотека идёт первым блоком, остальное — вторым, через пустую строку. Расставляет это `gofmt`.

Если имена пакетов конфликтуют, импорт переименовывают: `import mrand "math/rand"`.

Отдельно про `_` перед импортом — «импорт ради побочного эффекта»: пакет не используется напрямую, но его функция `init()` должна выполниться. Так подключают драйверы баз данных: `import _ "github.com/lib/pq"`.

## Циклические импорты запрещены

Жёсткое ограничение, к которому надо привыкнуть:

```
package github.com/example/shop/a
	imports github.com/example/shop/b from a.go
	imports github.com/example/shop/a from b.go: import cycle not allowed
```

Пакет `a` импортирует `b`, `b` импортирует `a` — сборка невозможна. В Java или Python такое допустимо, в Go нет.

Поначалу это раздражает, но ограничение полезное: оно заставляет продумывать направление зависимостей. Типичные решения:

- **вынести общее** в третий пакет, от которого зависят оба;
- **объявить интерфейс на стороне потребителя** — приём из статьи 11, снимающий большинство циклов;
- **пересмотреть границы**: если два пакета настолько связаны, возможно, это один пакет.

## Раскладка проекта

Стандарта, навязанного языком, нет, но сложились соглашения:

```
shop/
├── go.mod
├── cmd/
│   └── app/
│       └── main.go        // точка входа, тонкая
├── internal/
│   └── store/             // код только для этого модуля
├── pkg/
│   └── money/             // код, пригодный для внешних потребителей
```

**`cmd/`** — по папке на каждый исполняемый файл. Если программ несколько (сервер, миграции, CLI), у каждой своя папка с `package main`. Содержимое `main.go` — минимальное: разбор конфигурации, сборка зависимостей, запуск.

**`internal/`** — не соглашение, а **правило компилятора**. Пакеты внутри `internal` может импортировать только код из того же модуля:

```
main.go:3:8: no required module provides package github.com/example/shop/internal/store
```

Чужой модуль просто не увидит их. Это единственный способ в Go сказать «публично внутри проекта, но не наружу». Полезно даже в закрытых репозиториях: `internal` явно помечает, что интерфейс не обещан стабильным.

**`pkg/`** — для кода, который может понадобиться снаружи. Вокруг этой папки идут споры: многие считают её лишней и кладут пакеты прямо в корень. Оба варианта встречаются, выбирайте один и придерживайтесь.

**Практический совет: не начинайте с этой структуры.** Небольшой проект прекрасно живёт как два-три пакета в корне модуля. Раскладку вводят, когда файлов становится действительно много.

## `init()`

Функция `init()` выполняется автоматически при загрузке пакета, до `main`. Её может быть несколько в одном пакете, порядок между файлами не гарантирован.

```go
func init() {
	// подготовка пакета
}
```

Пользуйтесь ей осторожно: неявное выполнение усложняет чтение и ломает тесты. Почти всегда лучше явная функция инициализации, вызванная из `main`. Законное применение — регистрация в реестре, как это делают драйверы `database/sql` (статья 28).

## Что запомнить

- Пакет — это папка; имя пакета одно слово в нижнем регистре, без `utils` и `common`.
- Экспорт определяется регистром первой буквы; приватность работает на уровне пакета, а не типа.
- Путь импорта = имя модуля + путь папки; стандартная библиотека отделяется пустой строкой.
- `import _` подключает пакет ради его `init()`.
- Циклические импорты запрещены; лечатся выносом общего или интерфейсом у потребителя.
- `cmd/` — точки входа, `internal/` — код только для своего модуля (правило компилятора), `pkg/` — для внешних потребителей.
- Не вводите сложную раскладку заранее: маленькому проекту хватит нескольких пакетов в корне.
- `init()` выполняется до `main`; используйте редко и осознанно.

## Практика

**1. Первый пакет.** Создайте модуль с пакетом `greet`, экспортирующим одну функцию и скрывающим вспомогательную. Вызовите обе из `main` и объясните ошибку для второй. Готово, когда понимаете границу видимости.

**2. Приватность на уровне пакета.** В одном пакете опишите структуру с неэкспортированным полем и функцию (не метод), которая его читает. Убедитесь, что это работает, а из другого пакета — нет. Готово, когда разница ясна.

**3. Цикл импортов.** Создайте два пакета, импортирующих друг друга, и получите ошибку. Затем разорвите цикл, объявив интерфейс на стороне потребителя. Готово, когда проект собирается без третьего пакета.

**4. `internal`.** Разложите проект на `cmd/app`, `internal/store` и `pkg/money` по образцу из статьи. Затем во втором модуле попробуйте импортировать `internal`-пакет первого. Готово, когда получили отказ компилятора.

**5. Две программы.** Добавьте в `cmd/` вторую точку входа — утилиту, использующую те же внутренние пакеты. Соберите обе. Готово, когда получилось два бинарника, разделяющих код.
