# 19. `select`, таймауты и типичные ошибки

> ⏱ **~50 минут** · теория 20 мин · практика 30 мин

Канал из прошлой статьи умеет ждать одно событие. `select` умеет ждать несколько сразу — и именно из него строятся таймауты, отмена и главные циклы сервисов. Разберём конструкцию и заодно соберём в одном месте ошибки, на которых теряют время при работе с конкурентностью.

## `select`

Синтаксис похож на `switch`, но ветви — операции с каналами:

```go
select {
case v := <-fast:
	fmt.Println("победила:", v)
case v := <-slow:
	fmt.Println("победила:", v)
}
```

```
победила: быстрая
```

`select` блокируется, пока не будет готова хотя бы одна ветвь, выполняет её и завершается. **Одну ветвь за раз** — для повторения его оборачивают в цикл.

Если готовы несколько ветвей, выбор **случаен**:

```
случайный выбор: a=49 b=51
```

Сто итераций дали примерно поровну. Это защита от голодания: при последовательном выборе первая ветвь заглушала бы остальные. Полагаться на приоритет ветвей нельзя — его нет.

## Таймауты

Самое частое применение. `time.After` возвращает канал, в который через заданное время придёт значение:

```go
select {
case v := <-work(500 * time.Millisecond, "долгая"):
	fmt.Println(v)
case <-time.After(50 * time.Millisecond):
	fmt.Println("таймаут 50 мс")
}
```

```
таймаут 50 мс
```

Пять строк — и любая операция ограничена по времени.

Правило для сетевого кода: **у каждой внешней операции должен быть таймаут**. Зависший запрос без него держит горутину и её ресурсы вечно, а такие накапливаются до отказа сервиса.

Оговорка про `time.After`: он создаёт таймер, который живёт до срабатывания. В цикле на тысячи итераций это лишние аллокации — там берут `time.NewTimer` с явным `Stop()`. Для разовых вызовов `After` удобнее и вполне уместен.

## `default` — неблокирующие операции

Ветвь `default` выполняется, если не готова ни одна другая:

```go
select {
case v := <-ready:
	fmt.Println("есть значение", v)
default:
	fmt.Println("данных нет, не блокируемся")
}
```

`select` с `default` **никогда не блокируется**. Применения: проверить канал, не застревая; отправить, если есть место в буфере, и отбросить иначе (сброс метрик под нагрузкой).

Осторожно с этим внутри цикла: `for { select { ... default: } }` без паузы превращается в busy-loop, который сжигает ядро вхолостую.

## Главный цикл

Типичная конструкция долгоживущего сервиса — `select` в цикле с каналом завершения:

```go
ticker := time.NewTicker(20 * time.Millisecond)
defer ticker.Stop()

loop:
for {
	select {
	case <-ticker.C:
		ticks++
	case <-done:
		break loop
	}
}
```

```
тиков до остановки: 3
```

Две детали, которые легко упустить.

**`break` внутри `select` выходит из `select`, а не из цикла.** Отсюда метка `loop` — та же техника, что в статье 4. Альтернатива — `return`, если весь смысл функции в этом цикле.

**`ticker.Stop()` через `defer` обязателен.** Незакрытый тикер продолжает работать и удерживает ресурсы — классическая утечка.

## Выключение ветви через `nil`

Обещанное применение `nil`-канала из прошлой статьи:

```go
var disabled chan int          // nil
select {
case v := <-active:
	fmt.Println("из активного:", v)
case v := <-disabled:
	fmt.Println("никогда:", v)
}
```

Операции с `nil`-каналом блокируются вечно, поэтому такая ветвь **никогда не выбирается**. Приём используют, чтобы динамически отключать источники: присвоили каналу `nil` — ветвь выключилась, вернули значение — включилась. Так, например, перестают читать из исчерпанного источника, не переписывая `select`.

## Пустой `select`

```go
select {}
```

```
fatal error: all goroutines are asleep - deadlock!

goroutine 1 [select (no cases)]:
```

Блокируется навсегда. Иногда встречается в конце `main` у серверов, которые целиком работают в фоновых горутинах, — но лучше явно дожидаться сигнала завершения (статья 29).

## Типичные ошибки конкурентности

Соберём в одном месте то, на чём теряют время.

**Утечка горутин.** Горутина, заблокированная на канале, который никто не закроет, живёт до конца программы. Тысячи таких — и память кончилась. Симптом: растущий `runtime.NumGoroutine()`. Лечение — всегда предусматривать выход: таймаут, канал отмены, закрытие источника.

**Забытый `WaitGroup.Done`.** Программа зависает на `Wait`. Лечится `defer wg.Done()` первой строкой горутины.

**`break` вместо `break label`.** Цикл не прерывается, а тихо продолжается — ошибки нет, поведение неверное.

**Busy-loop с `default`.** Ядро загружено на 100%, работа не идёт.

**Гонка на общей переменной.** Разобрана в статье 17; проверяется `-race`.

**Отправка в закрытый канал.** Паника. Обычно означает, что закрывает не тот, кто должен.

**Паника в горутине.** Роняет всю программу (статья 14). Долгоживущим воркерам нужен свой `recover`.

Общее правило отладки: если программа зависла, отправьте ей `SIGQUIT` (`Ctrl+\`) — рантайм выведет стеки всех горутин с указанием, чего каждая ждёт. Это самый быстрый способ найти тупик.

## Что запомнить

- `select` ждёт несколько каналов и выполняет одну готовую ветвь; при нескольких готовых выбор случаен.
- Приоритета ветвей нет — полагаться на порядок нельзя.
- Таймаут делается ветвью `case <-time.After(d)`; у каждой внешней операции он должен быть.
- `default` делает `select` неблокирующим, но в цикле без паузы даёт busy-loop.
- `break` внутри `select` выходит из `select` — для выхода из цикла нужна метка.
- `ticker.Stop()` через `defer` обязателен, иначе утечка.
- Ветвь с `nil`-каналом никогда не выбирается — так их отключают динамически.
- Утечка горутин — самая частая проблема: у каждой должен быть предусмотрен выход.
- При зависании `Ctrl+\` печатает стеки всех горутин.

## Практика

**1. Гонка двух источников.** Запустите две горутины с разными задержками и через `select` определите победителя. Поменяйте задержки местами и убедитесь, что результат меняется. Готово, когда победитель предсказуем по времени.

**2. Таймаут.** Оберните операцию на 300 мс в `select` с таймаутом сначала 100 мс, затем 500 мс. Обработайте оба исхода. Готово, когда программа корректно печатает и успех, и таймаут.

**3. Неблокирующая отправка.** Сделайте канал ёмкостью 2 и попробуйте отправить в него пять значений через `select` с `default`, считая отброшенные. Готово, когда три значения отброшены без блокировки.

**4. Главный цикл.** Напишите сервис, который по тикеру раз в 50 мс печатает счётчик и завершается по сигналу из канала `done` через 300 мс. Сначала используйте обычный `break` и объясните, почему цикл не прервался. Готово, когда работает вариант с меткой и `ticker.Stop()`.

**5. Утечка горутин.** Напишите функцию, запускающую горутину, которая ждёт из канала, куда никто не пишет. Вызовите её 1000 раз и напечатайте `runtime.NumGoroutine()`. Затем добавьте канал отмены и убедитесь, что число вернулось к норме. Готово, когда утечка воспроизведена и устранена.
