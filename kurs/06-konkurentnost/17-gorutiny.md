# 17. Горутины и модель конкурентности

> ⏱ **~50 минут** · теория 20 мин · практика 30 мин

Конкурентность — то, ради чего Go чаще всего выбирают. Запустить конкурентную задачу здесь стоит одно ключевое слово и пару килобайт памяти, а не поток операционной системы. Разберём, как это устроено, и сразу столкнёмся с главной опасностью — гонкой данных.

## Горутина

Функция, запущенная со словом `go`, выполняется конкурентно:

```go
go fmt.Println("это может не напечататься")
fmt.Println("main не ждёт")
```

Формулировка в комментарии не случайна: `main` не ждёт запущенных горутин. **Когда завершается `main`, программа завершается целиком**, обрывая всё на полуслове. Это первое, обо что спотыкаются.

Чем горутина отличается от потока ОС:

| | Поток ОС | Горутина |
|---|---|---|
| Начальный стек | 1–8 МБ | ~2 КБ, растёт по мере надобности |
| Кто планирует | ядро | рантайм Go |
| Стоимость переключения | системный вызов | переключение в пространстве пользователя |
| Разумное количество | тысячи | сотни тысяч |

```go
for range 1000 {
	wg.Add(1)
	go func() { defer wg.Done(); time.Sleep(time.Millisecond) }()
}
```

```
1000 горутин за 2ms
```

Тысяча конкурентных задач за две миллисекунды. Тысяча потоков ОС заняла бы гигабайты памяти и заметное время на создание.

Работает это так: рантайм держит пул потоков ОС (по числу ядер) и распределяет горутины по ним. Когда горутина блокируется на вводе-выводе, планировщик снимает её с потока и ставит другую — поток не простаивает. Модель называют M:N — M горутин на N потоков.

Число потоков задаётся `GOMAXPROCS`, по умолчанию равным числу ядер:

```go
fmt.Println(runtime.NumCPU(), runtime.GOMAXPROCS(0))     // 12 12
```

Менять его почти никогда не нужно.

## Конкурентность ≠ параллелизм

Различие, на котором Роб Пайк построил известный доклад.

**Конкурентность** — про структуру программы: задачи независимы и могут выполняться в перекрывающиеся промежутки. **Параллелизм** — про исполнение: задачи действительно идут одновременно на разных ядрах.

Конкурентная программа на одном ядре не станет параллельной, но останется конкурентной — и всё равно выиграет, если задачи ждут ввода-вывода. Go даёт инструменты для конкурентности; параллелизм получается сам, когда ядер несколько.

## `sync.WaitGroup`

Раз `main` не ждёт горутин, нужен способ дождаться. Простейший — счётчик:

```go
var wg sync.WaitGroup

for i := 1; i <= 3; i++ {
	wg.Add(1)
	go worker(i, &wg)
}
wg.Wait()
```

```go
func worker(id int, wg *sync.WaitGroup) {
	defer wg.Done()
	// ...
}
```

Три правила:

1. **`Add` вызывают до запуска горутины**, а не внутри неё — иначе `Wait` может проскочить раньше, чем счётчик увеличится.
2. **`Done` ставят через `defer`** первой строкой — тогда он сработает и при панике, и при раннем `return`.
3. **`WaitGroup` передают по указателю.** Это структура; копия имеет собственный счётчик, и `Wait` зависнет навсегда. `go vet` такую ошибку ловит.

Обратите внимание на порядок вывода воркеров: `2, 1, 3`. Порядок выполнения горутин **не определён** — полагаться на него нельзя никогда.

## Гонка данных

А теперь главное. Тысяча горутин увеличивает общий счётчик:

```go
counter := 0
for range 1000 {
	wg.Add(1)
	go func() { defer wg.Done(); counter++ }()
}
wg.Wait()
fmt.Println(counter)
```

```
счётчик: 965
счётчик: 963
```

Не 1000. И каждый запуск даёт другое число.

Причина в том, что `counter++` — не одна операция, а три: прочитать, увеличить, записать. Две горутины читают одно значение, обе увеличивают его до одного и того же и записывают — одно увеличение потеряно.

Это **гонка данных** (data race): два конкурентных доступа к одной памяти, хотя бы один из которых — запись. Опасность в том, что программа не падает, а тихо считает неправильно, причём на слабой нагрузке может работать годами.

## Детектор гонок

Go даёт инструмент, который находит их автоматически:

```bash
go run -race ./rc
```

```
==================
WARNING: DATA RACE
Read at 0x00c0001aa018 by goroutine 7:
  main.main.func1()
      main.go:13 +0x68

Previous write at 0x00c0001aa018 by goroutine 8:
  main.main.func1()
      main.go:13 +0x78
```

Детектор показывает, кто читал, кто писал и где эти горутины созданы. Он замедляет программу в несколько раз, поэтому в проде его не включают, но **в тестах и CI он должен быть всегда**: `go test -race ./...`.

Правило: если вы пишете конкурентный код, запускайте его под `-race` до того, как он попадёт в прод. Это самая дешёвая проверка из возможных.

Способов исправить гонку два: не разделять данные вовсе, передавая их через каналы (статья 18), или защитить доступ мьютексом (статья 20).

## Переменная цикла

Историческая ловушка, о которой вы прочтёте в старых статьях:

```go
for i := range 5 {
	go func() { results[i] = i * i }()
}
```

```
[0 1 4 9 16]
```

Сейчас всё правильно. Но **до Go 1.22** переменная цикла была одна на все итерации, и все горутины видели её последнее значение — получалось `[16 16 16 16 16]` или случайный набор. Обходили это передачей параметра: `go func(i int) {...}(i)`.

Начиная с 1.22 переменная создаётся заново на каждой итерации, и проблема исчезла. Знать о ней стоит: старый код и старые советы в интернете полны этого обходного приёма.

## Что запомнить

- `go f()` запускает горутину; `main` её не ждёт и при завершении обрывает.
- Горутина стоит ~2 КБ против мегабайтов у потока ОС; сотни тысяч — нормально.
- Рантайм распределяет горутины по потокам ОС (модель M:N); `GOMAXPROCS` менять обычно не нужно.
- Конкурентность — про структуру программы, параллелизм — про одновременное исполнение.
- `WaitGroup`: `Add` до запуска, `Done` через `defer`, передавать по указателю.
- Порядок выполнения горутин не определён.
- Гонка данных не роняет программу, а тихо портит результат.
- `-race` находит гонки автоматически; в тестах и CI он обязателен.
- С Go 1.22 переменная цикла создаётся заново на каждой итерации.

## Практика

**1. Гонка на старте.** Запустите горутину без ожидания и убедитесь, что её вывод не появляется. Добавьте `time.Sleep`, затем замените его на `WaitGroup`. Готово, когда понимаете, почему `Sleep` — плохое решение.

**2. Цена горутины.** Запустите 100 000 горутин, каждая спит 100 мс, и замерьте общее время и потребление памяти (`runtime.MemStats`). Готово, когда есть числа и понимание, почему это возможно.

**3. Поймать гонку.** Воспроизведите потерянные увеличения счётчика. Запустите десять раз и запишите результаты. Затем запустите под `-race` и разберите вывод. Готово, когда можете объяснить, какие три операции скрыты за `counter++`.

**4. Ошибки `WaitGroup`.** Воспроизведите три ошибки: `Add` внутри горутины, забытый `Done`, передача `WaitGroup` по значению. Для последней проверьте, поймает ли её `go vet`. Готово, когда все три диагностированы.

**5. Параллельная обработка.** Разбейте большой слайс на четыре части и посчитайте сумму каждой в своей горутине, записывая результат в свой элемент слайса результатов. Проверьте под `-race`. Готово, когда гонки нет и сумма совпадает с однопоточной.
