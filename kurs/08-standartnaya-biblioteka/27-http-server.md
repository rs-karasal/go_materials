# 27. `net/http`: сервер и маршрутизация

> ⏱ **~55 минут** · теория 25 мин · практика 30 мин

HTTP-сервер в Go пишется на стандартной библиотеке — и это не учебное упрощение, а обычная практика в проде. С версии 1.22 в маршрутизатор добавили методы и параметры пути, закрыв главную причину, по которой раньше тянули внешние роутеры. Соберём работающий JSON-API целиком.

## Обработчик

Основа всего — интерфейс с одним методом:

```go
type Handler interface {
	ServeHTTP(w http.ResponseWriter, r *http.Request)
}
```

На практике пишут обычные функции и оборачивают их в `http.HandlerFunc` — это тип-адаптер, превращающий функцию в `Handler`:

```go
func handleHealth(w http.ResponseWriter, r *http.Request) {
	fmt.Fprint(w, "ok")
}
```

`w` — куда писать ответ (это `io.Writer`, так что работают `fmt.Fprint`, `json.NewEncoder` и всё остальное из статьи 11). `r` — запрос: путь, заголовки, тело, контекст.

## Маршрутизация

Начиная с Go 1.22 в шаблоне указывают метод и параметры пути:

```go
mux := http.NewServeMux()
mux.HandleFunc("GET /tasks", s.handleList)
mux.HandleFunc("POST /tasks", s.handleCreate)
mux.HandleFunc("GET /tasks/{id}", s.handleGet)
```

Параметр достают по имени:

```go
id := r.PathValue("id")
```

До 1.22 приходилось разбирать путь вручную или подключать `gorilla/mux` либо `chi`. Сейчас для большинства сервисов внешний роутер не нужен — берите его, только если нужны группы маршрутов с общими middleware или регулярные выражения в путях.

Правило разрешения: выигрывает **самый специфичный** шаблон. `/tasks/{id}` победит `/tasks/`, а точное совпадение победит оба.

## Ответы

Ключевое, что нужно запомнить про порядок:

```go
func writeJSON(w http.ResponseWriter, code int, v any) {
	w.Header().Set("Content-Type", "application/json")
	w.WriteHeader(code)
	if err := json.NewEncoder(w).Encode(v); err != nil {
		log.Println("не удалось записать ответ:", err)
	}
}
```

**Сначала заголовки, потом статус, потом тело.** `WriteHeader` фиксирует статус и отправляет заголовки; всё, что вы добавите в `w.Header()` после него, потеряется. Повторный вызов `WriteHeader` даёт предупреждение в лог и игнорируется.

Если `WriteHeader` не вызвать вовсе, первый же `Write` отправит 200.

Ошибки удобно отдавать через готовую функцию:

```go
http.Error(w, "некорректный JSON", http.StatusBadRequest)
```

Она ставит статус, тип `text/plain` и пишет сообщение. Для JSON-API обычно делают свой аналог, возвращающий ошибку структурой.

**Не забывайте `return` после `http.Error`.** Без него обработчик продолжит выполняться и попытается записать второй ответ — частая ошибка:

```go
if t.Title == "" {
	http.Error(w, "пустое название", http.StatusBadRequest)
	return
}
```

## Разбор запроса

```go
var t Task
if err := json.NewDecoder(r.Body).Decode(&t); err != nil {
	http.Error(w, "некорректный JSON", http.StatusBadRequest)
	return
}
```

Тело закрывать не нужно — сервер делает это сам (в отличие от клиента из прошлой статьи).

Остальное берут так: `r.URL.Query().Get("page")` — параметры строки запроса, `r.Header.Get("Authorization")` — заголовки, `r.Context()` — контекст запроса, который отменяется при разрыве соединения.

Обязательно проверяйте вход. Пришедший JSON — данные из внешнего мира; отсутствие поля даёт нулевое значение, а не ошибку (статья 25).

## Состояние сервера

Обработчики выполняются **каждый в своей горутине**. Значит, общее состояние требует защиты — статья 20:

```go
type Server struct {
	mu    sync.RWMutex
	tasks map[int]Task
	next  int
}
```

Обработчики — методы этого типа, поэтому доступ к зависимостям идёт через получатель, без глобальных переменных:

```go
func (s *Server) handleList(w http.ResponseWriter, r *http.Request) {
	s.mu.RLock()
	defer s.mu.RUnlock()
	// ...
}
```

Приём называют «сервер как структура», и он же решает вопрос внедрения зависимостей: в полях лежат база, логгер, конфигурация.

Маршруты собирают отдельным методом — так их видно одним списком:

```go
func (s *Server) routes() http.Handler {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /tasks", s.handleList)
	// ...
	return logging(mux)
}
```

## Middleware

Функция, принимающая `Handler` и возвращающая `Handler`, — вся концепция:

```go
func logging(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		start := time.Now()
		next.ServeHTTP(w, r)
		log.Printf("%s %s за %v", r.Method, r.URL.Path, time.Since(start))
	})
}
```

```
POST /tasks за 204µs
GET /tasks/1 за 16µs
```

Middleware складываются композицией: `logging(auth(recover(mux)))`. Порядок важен — внешний выполняется первым.

Типичный набор: логирование, восстановление после паники (статья 14 — иначе паника в одном обработчике уронит сервис), аутентификация, ограничение частоты запросов, CORS.

Тонкость: чтобы залогировать код ответа, `ResponseWriter` оборачивают своим типом, запоминающим статус в `WriteHeader`.

## Запуск

```go
srv := &http.Server{
	Addr:              ":8080",
	Handler:           s.routes(),
	ReadHeaderTimeout: 5 * time.Second,
	WriteTimeout:      10 * time.Second,
	IdleTimeout:       60 * time.Second,
}
log.Fatal(srv.ListenAndServe())
```

Есть короткая форма `http.ListenAndServe(":8080", handler)`, но у неё **нет таймаутов** — ровно та же проблема, что у `http.Get` из прошлой статьи. Медленный клиент способен удерживать соединения бесконечно, и это известный вектор атаки. Задавайте таймауты явно.

Корректное завершение по сигналу — тема следующей статьи.

## Тестирование

`httptest` работает и со стороны сервера, причём без поднятия настоящего порта:

```go
req := httptest.NewRequest("GET", "/tasks", nil)
w := httptest.NewRecorder()
s.routes().ServeHTTP(w, req)

if w.Code != http.StatusOK { ... }
```

`httptest.NewRecorder` записывает ответ в память. Такие тесты выполняются за микросекунды и проверяют весь путь, включая маршрутизацию и middleware.

## Что запомнить

- Обработчик — функция `(w http.ResponseWriter, r *http.Request)`; `w` является `io.Writer`.
- С Go 1.22 `ServeMux` понимает методы и параметры пути: `GET /tasks/{id}`, `r.PathValue("id")`.
- Порядок: заголовки → `WriteHeader` → тело; после `WriteHeader` заголовки менять поздно.
- После `http.Error` обязателен `return`.
- Тело запроса на сервере закрывать не нужно.
- Обработчики работают конкурентно — общее состояние защищают мьютексом.
- «Сервер как структура»: зависимости в полях, обработчики — методы, маршруты в одном месте.
- Middleware — функция `Handler → Handler`; внешний слой выполняется первым.
- `http.ListenAndServe` не имеет таймаутов — настраивайте `http.Server` явно.
- `httptest.NewRecorder` тестирует обработчики без сети.

## Практика

**1. Первый сервер.** Поднимите сервер с эндпоинтом `GET /ping`, отвечающим `pong`. Проверьте через `curl`. Готово, когда сервер отвечает.

**2. JSON-API.** Добавьте `POST /items` (принимает JSON, возвращает 201 с созданным объектом) и `GET /items/{id}`. Обработайте некорректный JSON и отсутствующий идентификатор. Готово, когда все четыре ответа корректны: 201, 200, 400, 404.

**3. Забытый `return`.** Намеренно уберите `return` после `http.Error` и посмотрите на предупреждение в логе о повторном `WriteHeader`. Готово, когда понимаете, что попадёт клиенту.

**4. Middleware.** Напишите два middleware: логирующий метод, путь и **код ответа**, и восстанавливающий после паники. Добавьте обработчик, который паникует, и убедитесь, что сервер выжил. Готово, когда в логе виден код 500, а сервис продолжает отвечать.

**5. Тесты обработчиков.** Покройте API из задачи 2 тестами через `httptest.NewRecorder`: успех, некорректный ввод, отсутствующая запись. Прогоните с `-race`. Готово, когда тесты проходят и гонок нет.
