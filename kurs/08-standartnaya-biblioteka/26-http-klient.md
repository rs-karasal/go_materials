# 26. `net/http`: клиент

> ⏱ **~45 минут** · теория 20 мин · практика 25 мин

HTTP-клиент в Go встроен в стандартную библиотеку и покрывает почти всё, что нужно на практике. Внешние обёртки обычно избыточны. Но у пакета есть несколько неочевидных мест, где ошибка стоит утечки ресурсов или зависшего сервиса, — их и разберём в первую очередь.

## Быстрый способ и почему он плох

```go
resp, err := http.Get(url)
```

Работает, но у этого вызова есть скрытая проблема: он использует `http.DefaultClient`, **у которого нет таймаута**. Запрос к неотвечающему серверу будет висеть бесконечно, удерживая горутину.

Поэтому в рабочем коде заводят свой клиент:

```go
var client = &http.Client{Timeout: 5 * time.Second}
```

`http.Client` **потокобезопасен и предназначен для переиспользования**: он держит пул соединений, и создание нового клиента на каждый запрос убивает keep-alive. Один клиент на приложение (или на внешний сервис) — правильная гранулярность.

## Полный запрос

```go
func fetchItem(ctx context.Context, url string) (*Item, error) {
	req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
	if err != nil {
		return nil, fmt.Errorf("создание запроса: %w", err)
	}
	req.Header.Set("Accept", "application/json")

	resp, err := client.Do(req)
	if err != nil {
		return nil, fmt.Errorf("выполнение запроса: %w", err)
	}
	defer resp.Body.Close()

	if resp.StatusCode != http.StatusOK {
		return nil, fmt.Errorf("неожиданный статус %s", resp.Status)
	}

	var item Item
	if err := json.NewDecoder(resp.Body).Decode(&item); err != nil {
		return nil, fmt.Errorf("разбор ответа: %w", err)
	}
	return &item, nil
}
```

Здесь собрано всё, что должно быть в любом клиентском вызове. Разберём по пунктам — каждый закрывает конкретную проблему.

**`NewRequestWithContext`**, а не `NewRequest`. Контекст из статьи 21 даёт отмену: закрыл пользователь вкладку — запрос к внешнему сервису прервался. Это отдельный механизм от `Timeout` у клиента и работает совместно с ним.

**`defer resp.Body.Close()`** — обязательно и сразу после проверки ошибки. Незакрытое тело **не возвращает соединение в пул**: под нагрузкой у вас кончатся файловые дескрипторы. Линтер `bodyclose` из статьи 24 существует ровно ради этой ошибки.

**Проверка статуса.** Самое неочевидное: **`err != nil` не означает успех HTTP-запроса**. Ошибка возвращается при сетевом сбое — DNS не разрешился, соединение отвергнуто, таймаут. Ответ 404 или 500 — это успешно выполненный запрос, и `err` будет `nil`:

```
статус: неожиданный статус 403 Forbidden
```

Забыть проверку `StatusCode` — типичная ошибка новичка: программа радостно разбирает тело страницы с ошибкой.

**Разбор через `Decoder`.** `json.NewDecoder(resp.Body).Decode(&v)` читает прямо из потока, без промежуточного слайса байтов — приём из прошлой статьи.

## Отмена по контексту

```go
shortCtx, cancel := context.WithTimeout(ctx, 50*time.Millisecond)
defer cancel()

_, err = fetchItem(shortCtx, srv.URL+"/slow")
errors.Is(err, context.DeadlineExceeded)     // true
```

Причина прерывания различима: `errors.Is` находит `context.DeadlineExceeded` внутри обёрнутой ошибки. Это позволяет отличить «сервис не успел» от «сервис ответил ошибкой» и отреагировать по-разному — например, повторить запрос.

## Отправка данных

Для простого случая есть `http.Post`:

```go
body := strings.NewReader(`{"name":"новый"}`)
resp, err := http.Post(url, "application/json", body)
```

Тело — любой `io.Reader` (статья 11): строка, файл, буфер, тело другого ответа. Для структуры удобно писать через `bytes.Buffer` и `json.NewEncoder`.

Оговорка та же: `http.Post` идёт через клиент без таймаута. В рабочем коде — `http.NewRequestWithContext` с методом `http.MethodPost` и `client.Do`.

## Тестирование клиента

Стандартная библиотека даёт поддельный сервер:

```go
srv := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
	w.Header().Set("Content-Type", "application/json")
	fmt.Fprint(w, `{"id":7,"name":"молоток"}`)
}))
defer srv.Close()

item, err := fetchItem(ctx, srv.URL+"/item")
```

`httptest.NewServer` поднимает настоящий HTTP-сервер на случайном порту и отдаёт его адрес в `srv.URL`. Никаких моков и подмены транспорта — тест проверяет реальный сетевой путь, оставаясь быстрым и изолированным.

Так тестируют и обработку ошибок: заставьте поддельный сервер вернуть 500 или заснуть на секунду и проверьте, что клиент реагирует правильно. Все примеры этой статьи выполнены именно так.

## Что стоит знать дополнительно

**Повторы.** Стандартный клиент не повторяет запросы. Логику повторов пишут сами: экспоненциальная задержка, ограничение числа попыток, повтор только для 5xx и сетевых ошибок — но не для 4xx.

**Настройка транспорта.** Пределы пула соединений задаются через `http.Transport`: `MaxIdleConnsPerHost`, `IdleConnTimeout`. Значения по умолчанию скромные, и на высокой нагрузке их поднимают.

**Чтение тела до конца.** Если вы прервали чтение раньше, соединение не переиспользуется. При отбрасывании тела делают `io.Copy(io.Discard, resp.Body)` перед `Close`.

## Что запомнить

- `http.Get` и `http.Post` используют клиент **без таймаута** — в рабочем коде создавайте свой `http.Client`.
- Клиент потокобезопасен и рассчитан на переиспользование; один на приложение.
- `http.NewRequestWithContext` даёт отмену независимо от таймаута клиента.
- `defer resp.Body.Close()` обязателен — иначе утечка соединений.
- `err == nil` не означает успех: коды 4xx и 5xx проверяют через `resp.StatusCode`.
- Причину сбоя различают через `errors.Is` — например, `context.DeadlineExceeded`.
- Тело запроса — любой `io.Reader`; ответ разбирают через `json.NewDecoder(resp.Body)`.
- `httptest.NewServer` поднимает настоящий сервер для тестов — моки не нужны.

## Практика

**1. Первый запрос.** Напишите функцию, забирающую JSON с публичного API и разбирающую его в структуру. Обработайте все три вида ошибок: сетевую, статус, разбор. Готово, когда каждая ветвь проверена.

**2. Забытый Close.** Напишите цикл из 200 запросов без `resp.Body.Close()` и посмотрите на число открытых соединений (`lsof` или `runtime.NumGoroutine`). Добавьте закрытие. Готово, когда разница видна.

**3. Статус против ошибки.** Сделайте запрос к адресу, возвращающему 404, и напечатайте `err` и `resp.StatusCode`. Готово, когда можете объяснить, почему `err` равен `nil`.

**4. Таймаут и отмена.** Отправьте запрос к медленному эндпоинту с таймаутом клиента 100 мс, затем — с контекстом на 50 мс. Различите причины через `errors.Is`. Готово, когда обе ситуации распознаются программно.

**5. Тест на `httptest`.** Покройте функцию из задачи 1 тремя тестами: успешный ответ, ответ 500, некорректный JSON. Используйте `httptest.NewServer`. Готово, когда все три проходят без обращения к настоящей сети.
