# 22. Тесты: `go test` и табличные тесты

> ⏱ **~50 минут** · теория 20 мин · практика 30 мин

Тестирование в Go встроено в язык и инструменты: не нужен фреймворк, не нужны библиотеки утверждений. Есть пакет `testing`, команда `go test` и одно соглашение об именах. Разберём базу и главную идиому — табличные тесты, которыми в Go написано большинство проверок.

## Первый тест

Файл должен заканчиваться на `_test.go`, функция — начинаться с `Test` и принимать `*testing.T`:

```go
func TestDivide(t *testing.T) {
	got, err := Divide(10, 2)
	if err != nil {
		t.Fatalf("неожиданная ошибка: %v", err)
	}
	if got != 5 {
		t.Errorf("Divide(10, 2) = %d, ожидалось 5", got)
	}
}
```

Файлы `_test.go` не попадают в сборку — они компилируются только при `go test`.

Библиотеки утверждений в стандартной поставке нет **намеренно**: авторы языка считают, что обычный `if` читается понятнее, чем `assert.Equal(t, 5, got)`. Взамен от сообщения об ошибке требуют информативности — принят формат «что вызвали = что получили, что ожидалось».

Два способа провалить тест:

| Метод | Что делает |
|---|---|
| `t.Errorf` | помечает провал, **продолжает** выполнение |
| `t.Fatalf` | помечает провал и **останавливает** тест |

Правило: `Fatal` — когда дальше проверять бессмысленно (получили ошибку вместо значения), `Error` — когда можно собрать больше информации за один прогон.

Есть ещё `t.Skip` для пропуска (например, при `testing.Short()`) и `t.Helper()` — им помечают вспомогательные функции, чтобы в отчёте указывалась строка вызова, а не строка внутри хелпера.

## Табличные тесты

Главная идиома Go. Вместо десяти похожих функций — срез случаев и один цикл:

```go
func TestTitle(t *testing.T) {
	tests := []struct {
		name    string
		in      string
		want    string
		wantErr error
	}{
		{name: "обычное слово", in: "привет", want: "Привет"},
		{name: "уже заглавная", in: "Привет", want: "Привет"},
		{name: "пустая строка", in: "", wantErr: ErrEmpty},
	}

	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			got, err := Title(tt.in)
			if !errors.Is(err, tt.wantErr) {
				t.Fatalf("ошибка = %v, ожидалась %v", err, tt.wantErr)
			}
			if got != tt.want {
				t.Errorf("Title(%q) = %q, ожидалось %q", tt.in, got, tt.want)
			}
		})
	}
}
```

Что это даёт:

- **Добавить случай — одна строка.** Порог для новой проверки минимален, и покрытие растёт само.
- **`t.Run` создаёт подтест** со своим именем: в отчёте видно, какой случай упал, и его можно запустить отдельно.
- **Анонимная структура** описывает ровно те поля, что нужны этому тесту.
- **`errors.Is` вместо сравнения** — правило из статьи 13; в поле `wantErr` для успешных случаев лежит `nil`, и проверка работает единообразно.

Именно так тестируют в стандартной библиотеке — открыв любой `_test.go` в исходниках Go, вы увидите эту конструкцию.

## Читаем вывод

Провалившийся тест выглядит так:

```
=== RUN   TestTitle
=== RUN   TestTitle/обычное_слово
    calc_test.go:44: Title("привет") = "\xbfривет", ожидалось "Привет"
--- FAIL: TestTitle (0.00s)
    --- FAIL: TestTitle/обычное_слово (0.00s)
    --- PASS: TestTitle/пустая_строка (0.00s)
```

Видно всё: какой подтест упал, на какой строке, с какими значениями. Кстати, эта ошибка настоящая — первая версия `Title` резала строку по байтам (`s[:1]`), и на кириллице получалась половина символа. Ровно тот случай из статьи 8, и тест поймал его сразу.

Пробелы в именах подтестов заменяются подчёркиваниями — учитывайте при фильтрации.

## Полезные команды

```bash
go test ./...                      # все пакеты
go test -v ./...                   # с подробным выводом
go test -run 'TestTitle/пустая'    # только подходящие по имени
go test -race ./...                # с детектором гонок
go test -cover ./...               # с покрытием
go test -count=1 ./...             # без кеша
```

Две команды, о которых стоит помнить особо.

**`-run` принимает регулярное выражение** и умеет адресовать подтесты через слеш — так отлаживают один случай из таблицы.

**`-count=1` отключает кеш.** Go кеширует результаты тестов, и если код не менялся, вы увидите `(cached)`. Обычно это удобно, но при тестах, зависящих от внешнего состояния, сбивает с толку.

## Параллельные тесты

Вызов `t.Parallel()` откладывает подтест и запускает его вместе с другими параллельными:

```go
t.Run("подтест", func(t *testing.T) {
	t.Parallel()
	// ...
})
```

```
=== PAUSE TestParallel/подтест
=== CONT  TestParallel/подтест
```

Это ускоряет прогон и заодно проверяет код на пригодность к конкурентному использованию — особенно в связке с `-race`.

Условие: параллельные тесты не должны делить изменяемое состояние. Общая переменная, один файл, одна тестовая база — источник плавающих провалов.

## Что и как тестировать

**Тесты живут рядом с кодом**, в том же пакете: `calc.go` и `calc_test.go`. Тогда доступны неэкспортированные функции.

Есть и вариант `package calc_test` — внешний тестовый пакет в той же папке. Он видит только публичный интерфейс, что полезно как проверка удобства API. Так тестируют библиотеки.

**Что покрывать в первую очередь:** граничные случаи (пусто, ноль, максимум), ошибочные пути, найденные баги. Тест на баг пишут **до** исправления — иначе не убедиться, что он ловит проблему.

**Чего избегать:** тестов на геттеры и тривиальные обёртки, погони за 100% покрытия. Покрытие показывает, какой код **выполнился**, а не какой проверен: тест без единого утверждения даёт те же проценты.

## Что запомнить

- Тесты лежат в файлах `_test.go`, функции начинаются с `Test` и принимают `*testing.T`.
- Библиотеки утверждений нет намеренно: обычный `if` плюс информативное сообщение.
- `t.Errorf` продолжает тест, `t.Fatalf` прерывает; `t.Helper()` исправляет номер строки в отчёте.
- Табличные тесты — основная идиома: срез случаев, `t.Run` для каждого.
- Ошибки в таблице сравнивают через `errors.Is`, а не `==`.
- `-run` фильтрует по регулярному выражению, включая подтесты через слеш.
- `-count=1` отключает кеш результатов.
- `t.Parallel()` ускоряет прогон и проверяет код на конкурентную пригодность.
- Тесты в том же пакете видят приватное; `package x_test` проверяет удобство публичного API.
- Покрытие показывает исполненный код, а не проверенный.

## Практика

**1. Первый тест.** Напишите функцию проверки високосного года и четыре теста: обычный год, високосный, столетие, столетие кратное 400. Готово, когда все четыре проходят.

**2. Перевод в таблицу.** Перепишите те же четыре теста одним табличным. Сравните объём кода. Готово, когда в отчёте `-v` видны четыре именованных подтеста.

**3. Error против Fatal.** Напишите тест, где после первой неудачной проверки идут ещё две. Прогоните с `Errorf` и с `Fatalf`, сравните вывод. Готово, когда понимаете, когда какой уместен.

**4. Фильтрация и кеш.** Запустите один подтест по имени через `-run`. Затем запустите весь пакет дважды подряд и найдите `(cached)`. Отключите кеш. Готово, когда все три команды отработали как ожидалось.

**5. Тест на баг.** Возьмите функцию `Title` из статьи, реализуйте её через `s[:1]` и напишите табличный тест с кириллицей — он должен упасть. Затем почините через руны. Готово, когда тест сначала падает, потом проходит.
