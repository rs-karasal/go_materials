# 24. Документация, линтеры и стиль Go

> ⏱ **~45 минут** · теория 20 мин · практика 25 мин

Go — язык с необычно сильной культурой единообразия. Форматирование задано инструментом, именование — устоявшимися соглашениями, документация пишется прямо в комментариях и никуда не выгружается. Эта статья про то, как писать код, который выглядит как код на Go, а не как перевод с Java.

## Документирующие комментарии

Комментарий перед объявлением становится документацией. Никакого специального синтаксиса вроде `@param` — просто текст:

```go
// Add добавляет задачу и возвращает её идентификатор.
// Возвращает [ErrEmptyTitle], если название пустое.
func (l *List) Add(title string) (int, error) {
```

Правила:

- **Начинайте с имени объявления.** «Add добавляет…», а не «Эта функция добавляет…». Так фраза читается и в списке, и вырванной из контекста.
- **Пишите предложениями**, с точкой в конце. Документация — не телеграмма.
- **Квадратные скобки создают ссылку**: `[ErrEmptyTitle]`, `[List]`, `[fmt.Stringer]`. Синтаксис появился в Go 1.19.
- **Отступ в четыре пробела делает блок кода** — так вставляют примеры.

Документация пакета — комментарий перед `package`, начинающийся со слов «Package имя»:

```go
// Package tasks управляет списком задач.
//
// Основной тип — [List]. Создайте его через [NewList]:
//
//	list := tasks.NewList()
//	id, err := list.Add("купить хлеб")
package tasks
```

Смотрят это командой `go doc`:

```
package tasks // import "example.com/tasks"

Package tasks управляет списком задач.

Основной тип — List. Создайте его через NewList:

    list := tasks.NewList()
    id, err := list.Add("купить хлеб")
```

`go doc .Add` покажет один символ, `go doc -all` — всё сразу. Локальный веб-сервер с документацией поднимает `pkgsite`; для публичных модулей то же самое доступно на pkg.go.dev автоматически.

**Что документировать обязательно:** пакет и всё экспортированное. Неэкспортированное — по необходимости. Пустая документация публичной функции — замечание на ревью.

Не забывайте про `Example`-функции из прошлой статьи: они попадают в документацию и проверяются тестами.

## Именование

Соглашения Go отличаются от привычных в Java и Python, и отличаются заметно.

**Короткие имена в узкой области видимости.** `i`, `r`, `buf`, `err` — норма для нескольких строк. Чем шире область, тем длиннее имя. Обратное правило тоже верно: `userServiceInstance` в трёхстрочной функции выглядит чужеродно.

**Получатель метода — одна-две буквы**, одинаково во всех методах типа: `func (l *List)`. Слов `this` и `self` в Go не пишут.

**Никаких префиксов и суффиксов.** Не `IUser`, не `UserImpl`, не `user_name`. Только `CamelCase` и `camelCase`.

**Аббревиатуры целиком в одном регистре**: `userID`, `HTTPServer`, `parseURL` — не `userId` и не `HttpServer`.

**Имя пакета — часть имени.** `http.Server`, а не `http.HTTPServer`; `bytes.Buffer`, а не `bytes.ByteBuffer`.

**Интерфейсы с одним методом называют по методу с суффиксом `-er`:** `Reader`, `Writer`, `Stringer`, `Closer`.

**Геттеры без `Get`.** Метод, возвращающий поле `name`, называют `Name()`, а не `GetName()`. Сеттер при этом — `SetName()`.

## Линтеры

`gofmt` и `go vet` вы знаете со статьи 2. В рабочих проектах к ним добавляют более строгие инструменты.

**`staticcheck`** — де-факто стандарт. Находит то, что `vet` пропускает: недостижимый код, бесполезные присваивания, неэффективные конструкции, неправильное использование стандартной библиотеки.

**`golangci-lint`** — агрегатор, запускающий десятки линтеров разом, с конфигурацией в `.golangci.yml`. То, что обычно ставят в CI.

Полезные линтеры внутри него:

| Линтер | Что находит |
|---|---|
| `errcheck` | проигнорированные ошибки |
| `ineffassign` | присваивания, результат которых не используется |
| `unused` | неиспользуемый код |
| `gocritic` | стилистические и логические замечания |
| `bodyclose` | незакрытые тела HTTP-ответов |

Начинать стоит с набора по умолчанию: слишком строгая конфигурация на старте порождает шум, который команда учится игнорировать.

## Идиомы, отличающие Go-код

Несколько вещей, по которым видно, что автор освоился с языком.

**Ранний возврат вместо вложенности.** Вместо лестницы `if ok { ... }` пишут проверку ошибки и `return` — счастливый путь остаётся на левом краю:

```go
if err != nil {
	return err
}
// основная логика без вложенности
```

**Обработка ошибки сразу после вызова.** Не собирайте ошибки, чтобы разобрать их позже.

**Интерфейсы у потребителя, маленькие** — статья 11.

**Нулевое значение делают рабочим** — статья 3. Это избавляет пользователя от конструктора.

**Принимайте интерфейсы, возвращайте структуры.** Функция принимает `io.Reader` (максимум гибкости для вызывающего), но возвращает конкретный `*Client` (максимум информации для пользователя).

**Явное лучше неявного.** Магии в Go не любят: пусть будет три строки вместо хитрой рефлексии.

## Что запомнить

- Документация — обычный комментарий перед объявлением, начинающийся с имени.
- `[Имя]` в комментарии создаёт ссылку; отступ в четыре пробела — блок кода.
- Комментарий пакета начинается со слов «Package имя»; документируйте всё экспортированное.
- Короткие имена в узкой области, длинные — в широкой; получатель метода в одну-две буквы.
- Аббревиатуры пишут одним регистром (`userID`, `HTTPServer`), геттеры — без `Get`.
- Однометодные интерфейсы называют по методу с суффиксом `-er`.
- `staticcheck` и `golangci-lint` дополняют `go vet` в рабочих проектах.
- Ранний возврат вместо вложенности; принимайте интерфейсы, возвращайте структуры.

## Практика

**1. Документация пакета.** Возьмите свой пакет из практики статьи 15 и напишите документацию: комментарий пакета с примером, комментарии ко всем экспортированным сущностям, ссылки в квадратных скобках. Проверьте через `go doc -all`. Готово, когда вывод читается как справка.

**2. Переименование.** Возьмите код, написанный в стиле другого языка (`GetUserName`, `IUserService`, `userId`), и приведите к соглашениям Go. Готово, когда ни одно имя не нарушает правил из статьи.

**3. Линтер.** Установите `staticcheck`, прогоните его по своему коду из предыдущих статей и исправьте замечания. Готово, когда вывод пуст, а вы понимаете каждое исправление.

**4. Ранний возврат.** Найдите или напишите функцию с тремя уровнями вложенности `if` и перепишите её через ранние возвраты. Сравните читаемость. Готово, когда основной путь идёт по левому краю.

**5. Приём интерфейсов.** Напишите функцию, читающую данные, которая принимает `io.Reader`. Вызовите её от файла, от строки (`strings.NewReader`) и от сетевого ответа. Готово, когда одна функция обслужила три разных источника.
