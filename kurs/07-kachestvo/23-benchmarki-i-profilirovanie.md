# 23. Бенчмарки, покрытие и профилирование

> ⏱ **~50 минут** · теория 20 мин · практика 30 мин

Go даёт измерительные инструменты в той же поставке, что и тесты: бенчмарки, отчёт о покрытии и профилировщик. Порог входа низкий, а польза прямая — вместо споров о том, что быстрее, вы получаете числа. Разберём их и договоримся, когда вообще стоит этим заниматься.

## Бенчмарк

Функция начинается с `Benchmark` и принимает `*testing.B`:

```go
func BenchmarkBuilder(b *testing.B) {
	for b.Loop() {
		builder(1000)
	}
}
```

`b.Loop()` (Go 1.24) сам подбирает число итераций, чтобы измерение было статистически осмысленным. В старом коде вы встретите `for i := 0; i < b.N; i++` — это предыдущая форма, она продолжает работать.

Запуск:

```bash
go test -bench=. -benchmem ./...
```

```
goos: darwin
goarch: arm64
cpu: Apple M3 Pro
BenchmarkConcat-12              7491    159241 ns/op   1507563 B/op   2734 allocs/op
BenchmarkBuilder-12            35499     34040 ns/op     14431 B/op    756 allocs/op
BenchmarkBuilderPrealloc-12    36619     32563 ns/op     10085 B/op    746 allocs/op
```

Читаем колонки:

- **`-12`** — значение `GOMAXPROCS`, то есть число ядер;
- **`7491`** — сколько раз выполнилось тело;
- **`159241 ns/op`** — наносекунд на операцию, главное число;
- **`1507563 B/op`** — байт выделено на операцию;
- **`2734 allocs/op`** — число выделений памяти.

Флаг `-benchmem` даёт две последние колонки, и без него бенчмарк почти бесполезен: в Go производительность чаще упирается в аллокации, чем в вычисления.

Цифры подтверждают правило из статьи 8: конкатенация строк в цикле медленнее `strings.Builder` **в 4,7 раза** и выделяет памяти в сто раз больше. Предварительный `Grow` даёт ещё несколько процентов.

Полезные флаги: `-benchtime=10s` (дольше и точнее), `-count=5` (несколько прогонов), `-bench=Builder` (только подходящие по имени).

Для сравнения версий есть утилита `benchstat`: она прогоняет статистику и показывает, значима ли разница или это шум.

## Ловушки измерений

**Оптимизирующий компилятор.** Если результат функции никуда не идёт, вызов могут выкинуть целиком, и вы измерите пустой цикл. Лечение — присвоить результат переменной уровня пакета.

**Подготовка внутри цикла.** Создание тестовых данных попадёт в измерение. Готовьте до цикла, а если это невозможно — останавливайте таймер: `b.StopTimer()` / `b.StartTimer()`.

**Шумная машина.** Открытый браузер и сборка в фоне легко дают разброс в десятки процентов. Меряйте на спокойной машине и повторяйте прогон.

## Покрытие

```bash
go test -cover ./...
```

```
ok  ex/g22  0.698s  coverage: 100.0% of statements
```

Подробный отчёт по функциям:

```bash
go test -coverprofile=cover.out ./...
go tool cover -func=cover.out
```

```
ex/g22/calc.go:11:  Divide  100.0%
ex/g22/calc.go:18:  Title   100.0%
total:              (statements)  100.0%
```

А команда `go tool cover -html=cover.out` открывает браузер с исходником, где непокрытые строки подсвечены красным. Это самый полезный режим: он показывает **какие именно** ветви не проверены.

Повторим предостережение из прошлой статьи: покрытие измеряет исполненный код, а не проверенный. Тест без единого утверждения даёт те же проценты. Пользуйтесь отчётом, чтобы найти забытые ветки обработки ошибок, а не чтобы отчитываться цифрой.

## Примеры как тесты

Функция с префиксом `Example` и комментарием `// Output:` одновременно документация и тест:

```go
func ExampleTitle() {
	s, _ := Title("привет")
	fmt.Println(s)
	// Output: Привет
}
```

`go test` сравнивает напечатанное с комментарием. Пример попадает в документацию пакета и **не может устареть**: изменится поведение — тест упадёт. Имя связывает пример с сущностью: `ExampleTitle`, `ExampleClient_Get`.

## Профилирование

Когда бенчмарк показал проблему, профилировщик покажет, где именно.

```bash
go test -bench=. -cpuprofile=cpu.out -memprofile=mem.out ./...
go tool pprof cpu.out
```

В интерактивной оболочке `pprof` полезны три команды: `top` — самые дорогие функции, `list Имя` — построчные затраты внутри функции, `web` — граф вызовов в браузере (требует graphviz).

Для работающего сервиса профиль снимают на живую, подключив `net/http/pprof`:

```go
import _ "net/http/pprof"
```

Пакет регистрирует обработчики на `/debug/pprof/` — тот самый импорт ради побочного эффекта из статьи 15. Дальше профиль снимается с работающего процесса:

```bash
go tool pprof http://localhost:6060/debug/pprof/heap
```

Важно: такие эндпоинты **не выставляют наружу** — только на внутреннем порту или за аутентификацией.

Основные виды профилей: `cpu` (где тратится процессор), `heap` (кто выделяет память), `goroutine` (сколько горутин и где стоят — лучший инструмент для поиска утечек из статьи 19), `mutex` и `block` (конкуренция за блокировки).

## Когда всё это нужно

Порядок действий, который экономит время:

1. **Сначала работает, потом быстро.** Оптимизация без измерений — потеря времени в 90% случаев.
2. **Измерьте.** Бенчмарк или профиль на реальных данных.
3. **Найдите узкое место.** Обычно это одна-две функции, и почти всегда это лишние аллокации, а не арифметика.
4. **Исправьте и снова измерьте.** Без этого шага вы не знаете, помогло ли.

Типичные источники медленного кода в Go: конкатенация строк в цикле, слайсы без резерва `cap`, лишние преобразования `[]byte` ↔ `string`, `any` в горячем пути (статья 12), незакрытые ресурсы.

## Что запомнить

- Бенчмарк — функция `BenchmarkX(b *testing.B)` с циклом `for b.Loop()`.
- `-benchmem` показывает аллокации; в Go они чаще узкое место, чем вычисления.
- Компилятор может выкинуть вызов, результат которого не используется.
- Подготовку данных выносят из измеряемого цикла или отключают таймер.
- `go tool cover -html` подсвечивает непокрытые строки — самый полезный режим.
- Покрытие показывает исполненный код, а не проверенный.
- `Example`-функции с `// Output:` — одновременно документация и тест.
- `pprof` даёт профили cpu, heap, goroutine, mutex; `net/http/pprof` снимает их с живого сервиса, но наружу не выставляется.
- Оптимизируйте только после измерения и измеряйте после исправления.

## Практика

**1. Первый бенчмарк.** Напишите бенчмарки для конкатенации строк и `strings.Builder` на 1000 элементов. Запустите с `-benchmem`. Готово, когда есть числа и вы видите разницу в аллокациях.

**2. Резерв слайса.** Сравните заполнение слайса на миллион элементов с `make([]int, 0)` и с указанием `cap`. Готово, когда разница в `allocs/op` объяснима через статью 6.

**3. Ловушка оптимизатора.** Напишите бенчмарк, результат которого никуда не идёт, и посмотрите на подозрительно малое `ns/op`. Затем присвойте результат переменной пакета. Готово, когда числа изменились и вы понимаете почему.

**4. Отчёт о покрытии.** Напишите функцию с тремя ветвями, покройте две и откройте HTML-отчёт. Готово, когда непокрытая ветвь подсвечена и добавлен тест на неё.

**5. Профиль.** Снимите CPU-профиль с бенчмарка конкатенации и найдите через `top` и `list` самую дорогую функцию. Готово, когда можете назвать строку, где тратится время.
