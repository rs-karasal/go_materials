# 18. Каналы

> ⏱ **~55 минут** · теория 25 мин · практика 30 мин

«Не общайтесь, разделяя память; разделяйте память, общаясь» — девиз, определяющий подход Go к конкурентности. Вместо блокировок вокруг общих данных горутины передают их друг другу по каналам. Гонки при этом исчезают сами: у данных в каждый момент один владелец.

## Небуферизованный канал

```go
ch := make(chan string)
go func() { ch <- "привет из горутины" }()
fmt.Println(<-ch)
```

Стрелка показывает направление: `ch <- v` отправить, `<-ch` получить.

Ключевое свойство: небуферизованный канал **синхронизирует** горутины. Отправитель блокируется, пока кто-то не заберёт значение; получатель — пока кто-то не отправит. Обмен происходит одновременно, это называется «рандеву».

Отсюда классический тупик:

```go
ch := make(chan int)
ch <- 1        // некому получить
```

```
fatal error: all goroutines are asleep - deadlock!

goroutine 1 [chan send]:
```

Рантайм заметил, что все горутины спят, и завершил программу. Сообщение полезное: в квадратных скобках указано, чего именно ждёт каждая горутина — `chan send`, `chan receive`, `semacquire`.

## Буферизованный канал

```go
buf := make(chan int, 3)
buf <- 1
buf <- 2
fmt.Printf("len=%d cap=%d\n", len(buf), cap(buf))     // len=2 cap=3
```

Второй аргумент `make` задаёт ёмкость. Отправка блокируется, только когда буфер полон, получение — когда пуст.

Что выбрать? **По умолчанию берите небуферизованный.** Он даёт строгую синхронизацию и сразу выявляет ошибки в логике. Буфер добавляют осознанно: чтобы сгладить всплески нагрузки или когда точно известно число сообщений.

Важно понимать: буфер **не устраняет** блокировку, а откладывает её. Ёмкость канала — это ещё и **обратное давление**: заполнившийся буфер притормаживает производителя, не давая памяти расти бесконечно.

## Закрытие и перебор

Закрывает канал **отправитель** — сообщая «данных больше не будет»:

```go
close(ch)
```

Получатель узнаёт об этом двумя способами. Через `range`, который завершается сам:

```go
func consume(ch <-chan int) int {
	total := 0
	for v := range ch {
		total += v
	}
	return total
}
```

Или через форму «comma ok» — ту же, что у карт и приведения типов:

```go
v, ok := <-closed
```

```
из закрытого с данными: 42 true
из пустого закрытого: 0 false
```

Пока в буфере есть данные, они выдаются даже после закрытия. Затем канал бесконечно отдаёт нулевое значение с `ok == false`.

Три правила про закрытие:

1. **Закрывает только отправитель.** Получатель не знает, есть ли другие отправители.
2. **Отправка в закрытый канал — паника:**

```
panic: send on closed channel
```

3. **Повторное закрытие — тоже паника.** Если отправителей несколько, закрывать напрямую нельзя: договариваются через `WaitGroup`.

Именно так закрывают канал при нескольких производителях:

```go
var wg sync.WaitGroup
wg.Add(2)
go producer(nums, 5, &wg)
go producer(nums, 5, &wg)
go func() { wg.Wait(); close(nums) }()
```

Отдельная горутина ждёт всех производителей и закрывает канал. Без неё `range` на получателе завис бы навсегда.

Закрывать канал не обязательно, если получатель и так знает, сколько сообщений ждёт. Сборщик мусора уберёт незакрытый канал сам — утечки не будет.

## Направленные каналы

В сигнатурах указывают направление:

```go
func producer(ch chan<- int, ...)     // только отправка
func consume(ch <-chan int) int       // только получение
```

Компилятор запретит получать из `chan<-` и отправлять в `<-chan`. Двусторонний канал приводится к направленному автоматически, обратно — нет.

Это дешёвая документация: по сигнатуре видно роль функции. **Пишите направление всегда, когда оно известно.**

## Канал как сигнал

Распространённая идиома — канал, по которому не передают данные, а только сообщают о событии:

```go
done := make(chan struct{})
go func() {
	// работа
	close(done)
}()
<-done
```

Тип `struct{}` не занимает памяти (тот же приём, что для множеств в статье 7). Закрытие канала разблокирует **всех** ожидающих сразу — это способ оповестить любое число горутин одним действием. На нём построена отмена в `context` (статья 21).

## Каналы как средство сбора результатов

Горутины пишут в общий канал, `main` читает по мере готовности:

```go
results := make(chan string)
for i := range 3 {
	go func() { results <- fmt.Sprintf("задача %d", i) }()
}
for range 3 {
	fmt.Println("получено:", <-results)
}
```

```
получено: задача 2
получено: задача 1
получено: задача 0
```

Порядок — по времени завершения, а не по запуску. Никаких мьютексов: канал сам сериализует доступ.

## `nil`-канал

Нулевое значение канала — `nil`, и операции с ним **блокируются навсегда**:

```
fatal error: all goroutines are asleep - deadlock!

goroutine 1 [chan receive (nil chan)]:
```

Звучит как чистое зло, но у этого есть законное применение: в `select` ветвь с `nil`-каналом никогда не выбирается, и это используют, чтобы выключать ветви на ходу. Разберём в следующей статье.

## Что запомнить

- Каналы передают данные между горутинами, устраняя гонки: у значения один владелец.
- Небуферизованный канал синхронизирует отправителя и получателя; буферизованный блокирует только на границах буфера.
- По умолчанию берите небуферизованный; буфер — осознанное решение и средство обратного давления.
- Тупик диагностируется рантаймом: `all goroutines are asleep — deadlock!` с указанием, чего ждут.
- Закрывает канал отправитель; отправка в закрытый и повторное закрытие — паника.
- При нескольких производителях закрывают из отдельной горутины после `WaitGroup.Wait()`.
- `range` по каналу завершается при закрытии; `v, ok := <-ch` отличает закрытие.
- Направленные каналы (`chan<-`, `<-chan`) документируют роль функции.
- `close(done)` с каналом `struct{}` оповещает всех ожидающих сразу.
- Операции с `nil`-каналом блокируются навсегда.

## Практика

**1. Рандеву.** Напишите программу, где `main` получает значение из горутины через небуферизованный канал. Затем уберите `go` и объясните тупик. Готово, когда сообщение рантайма понятно.

**2. Буфер и блокировка.** Создайте канал ёмкостью 2, отправьте три значения без получателя и посмотрите на тупик. Печатайте `len` и `cap` после каждой отправки. Готово, когда видно, на какой именно отправке всё встало.

**3. Закрытие с несколькими производителями.** Запустите три горутины-производителя в один канал и корректно закройте его. Получатель должен работать через `range`. Готово, когда программа завершается без тупика и без паники.

**4. Ошибки закрытия.** Воспроизведите две паники: отправку в закрытый канал и повторное закрытие. Готово, когда обе получены и вы знаете, как их избегать.

**5. Конвейер.** Постройте цепочку из трёх стадий: генератор чисел → возведение в квадрат → фильтр чётных. Каждая стадия — своя горутина, связь через каналы, каждая закрывает свой выходной канал. Готово, когда результат приходит потоком, а все горутины завершаются.
