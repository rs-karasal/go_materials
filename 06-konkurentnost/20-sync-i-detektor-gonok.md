# 20. `sync`: `Mutex`, `WaitGroup`, `atomic` и детектор гонок

> ⏱ **~50 минут** · теория 20 мин · практика 30 мин

Каналы решают задачу передачи данных. Но иногда состояние действительно общее — кэш, счётчик метрик, реестр подключений, — и передавать его некому. Тогда доступ защищают примитивами из пакета `sync`. Разберём их и договоримся, когда что выбирать.

## `sync.Mutex`

Мьютекс пускает к защищаемым данным одну горутину за раз:

```go
type SafeCounter struct {
	mu sync.Mutex
	n  map[string]int
}

func (c *SafeCounter) Inc(key string) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.n[key]++
}
```

```
под мьютексом: 1000
```

Тысяча горутин, ровно 1000 — гонка из статьи 17 исчезла.

Соглашения, которые стоит соблюдать:

**Мьютекс кладут рядом с данными, которые он защищает**, — обычно первым полем структуры. Так видно, что именно он охраняет.

**`Unlock` через `defer`** сразу после `Lock`: сработает при любом выходе, включая панику.

**Нулевое значение готово к работе** — `var mu sync.Mutex` достаточно, инициализация не нужна.

**Методы с мьютексом объявляют на указателе.** Получатель-значение копирует структуру вместе с мьютексом, и защита исчезает:

```go
func (c C) Bad() { c.mu.Lock(); c.n++; c.mu.Unlock() }
```

```
cm/main.go:13:9: Bad passes lock by value: C contains sync.Mutex
```

Это ловит `go vet` — ещё один повод держать его в CI.

Повторный захват того же мьютекса — тупик: `sync.Mutex` не рекурсивный.

```
fatal error: all goroutines are asleep - deadlock!

goroutine 1 [sync.Mutex.Lock]:
```

## `sync.RWMutex`

Когда чтений намного больше, чем записей, мьютекс становится узким местом: читатели не мешают друг другу, но всё равно стоят в очереди.

```go
func (c *Cache) Get(k string) (string, bool) {
	c.mu.RLock()
	defer c.mu.RUnlock()
	v, ok := c.data[k]
	return v, ok
}

func (c *Cache) Set(k, v string) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.data[k] = v
}
```

`RLock` пускает сколько угодно читателей одновременно, `Lock` — одного писателя эксклюзивно. Правило то же, что у ссылок и каналов: много читателей **либо** один писатель.

Не хватайтесь за `RWMutex` по умолчанию: он сложнее и на коротких критических секциях медленнее обычного мьютекса из-за большего учёта. Переходите на него, когда профилирование показало конкуренцию на чтении.

## `sync/atomic`

Для простых счётчиков мьютекс избыточен — есть атомарные операции, выполняемые процессором неделимо:

```go
var counter atomic.Int64
counter.Add(5)
fmt.Println(counter.Load())
```

Типы `atomic.Int64`, `atomic.Bool`, `atomic.Pointer[T]`, `atomic.Value` появились в Go 1.19 и удобнее старых функций `atomic.AddInt64(&x, 1)`: невозможно случайно обратиться к переменной напрямую, минуя атомарность.

Границы применимости узкие: атомарно можно менять **одно** значение. Как только нужно согласованно изменить два поля — берите мьютекс.

## `sync.Once`

Гарантирует, что функция выполнится ровно один раз, сколько бы горутин её ни вызвали:

```go
var once sync.Once

func setup() {
	once.Do(func() {
		initTime = time.Now()
		fmt.Println("инициализация выполнена один раз")
	})
}
```

```
инициализация выполнена один раз
```

Пять горутин — одно сообщение. Применение: ленивая инициализация соединения, загрузка конфигурации, регистрация. Остальные вызовы **дожидаются** завершения первого, а не проскакивают мимо.

## Что ещё есть

- **`sync.Map`** — карта для конкурентного доступа. Вопреки ожиданиям, она **не** является заменой обычной карты с мьютексом: оптимизирована под сценарий «пишем один раз, читаем много» и в остальных случаях медленнее. Начинайте с `map` + `Mutex`.
- **`sync.Pool`** — пул переиспользуемых объектов, снижает нагрузку на сборщик мусора. Нужен при доказанной проблеме с аллокациями.
- **`errgroup`** (из `golang.org/x/sync`) — `WaitGroup`, который собирает ошибки и умеет отменять остальные задачи при первой неудаче. В реальных проектах используется постоянно.

## Каналы или мьютексы

Вопрос, который задают все.

**Каналы** — когда данные **передаются**: конвейер, раздача заданий воркерам, сбор результатов, сигнал завершения. Владение переходит вместе со значением.

**Мьютексы** — когда состояние **общее** и никуда не движется: кэш, счётчики, реестр. Каналы здесь дадут громоздкую конструкцию.

**`atomic`** — для одного числа или флага.

Официальная формулировка из вики Go: «используйте то, что выразительнее». Девиз про «разделяйте память, общаясь» — это рекомендация по умолчанию, а не запрет на мьютексы: стандартная библиотека полна `sync.Mutex`.

## Детектор гонок

Повторим главное из статьи 17, потому что здесь это критично:

```bash
go test -race ./...
go run -race .
```

Детектор находит гонки во время выполнения — но только на тех путях, которые реально исполнились. Отсюда правило: **запускайте тесты конкурентного кода под `-race` в CI**, и пусть тесты нагружают код параллельно.

Замедление в 5–10 раз и рост потребления памяти делают его непригодным для прода, но на тестах это приемлемая цена.

## Что запомнить

- `Mutex` пускает одну горутину; кладите его рядом с данными, `Unlock` — через `defer`.
- Нулевое значение мьютекса готово к работе; методы объявляйте на указателе, иначе защита копируется.
- `go vet` ловит передачу мьютекса по значению.
- `RWMutex` пускает много читателей либо одного писателя; берите его по результатам профилирования, а не заранее.
- `atomic` подходит для одного значения; для двух согласованных полей нужен мьютекс.
- `sync.Once` выполняет инициализацию ровно один раз, остальные вызовы ждут.
- `sync.Map` — не универсальная замена карте с мьютексом.
- Каналы — когда данные передаются, мьютексы — когда состояние общее.
- `-race` обязателен в тестах и CI; он находит гонки только на исполненных путях.

## Практика

**1. Счётчик под защитой.** Возьмите код с гонкой из статьи 17 и почините тремя способами: мьютексом, `atomic` и каналом. Проверьте каждый под `-race`. Готово, когда все три дают 1000.

**2. Копия мьютекса.** Опишите структуру с мьютексом и метод с получателем-значением. Убедитесь, что защита не работает, и что `go vet` это находит. Готово, когда ошибка воспроизведена и исправлена.

**3. Кэш с `RWMutex`.** Реализуйте потокобезопасный кэш с методами `Get` и `Set`. Нагрузите его 100 читателями и 5 писателями. Сравните время с версией на обычном `Mutex`. Готово, когда есть два числа.

**4. Ленивая инициализация.** Напишите функцию, возвращающую «тяжёлый» объект, создаваемый через `sync.Once`. Вызовите её из 50 горутин и убедитесь, что создание произошло один раз. Готово, когда счётчик созданий равен единице.

**5. Тупик и его диагностика.** Создайте два мьютекса и две горутины, захватывающие их в противоположном порядке. Добейтесь зависания, затем найдите причину по стекам (`Ctrl+\`) и почините единым порядком захвата. Готово, когда обе версии воспроизведены осознанно.
