# Правила работы над материалами по Go

Рабочий документ. Живёт и дополняется по мере набора опыта — если по ходу написания статей находится удачный приём или, наоборот, грабли, они фиксируются здесь (см. «Журнал улучшений» в конце).

Правила во многом наследуют подход из репозитория `rust_materials`, но рамка другая: Rust осваивается с нуля через письмо, Go — область экспертизы автора, и статьи здесь пишутся как продукт для библиотеки материалов, а не как конспект обучения.

---

## 1. Суть проекта

Связный курс по Go для самостоятельного изучения: от полного нуля до уверенного джуна. Каждая тема — одна статья.

Целевая аудитория — человек, который уже программирует на другом языке, но Go не знает. Не «эксперт по системному программированию» и не «полный новичок в программировании».

Отдельная задача курса — **снять ложные ожидания**. В Go приходят из Python, Java и JavaScript и пытаются писать как раньше: искать классы, наследование, исключения, дженерики на каждый чих. Курс должен объяснять не только «как», но и «почему в Go этого нет и что вместо».

## 2. Формат статьи

Обязательная структура. Порядок разделов не меняется.

```markdown
# <Номер>. <Название темы>

> ⏱ **~45 минут** · теория 15 мин · практика 30 мин

<Лид: 2–4 предложения. Что за тема, зачем она нужна и что читатель
сможет делать после статьи. Без воды и без «в этой статье мы рассмотрим».>

## <Смысловой раздел 1>
## <Смысловой раздел 2>
## <Смысловой раздел 3–5>

## Что запомнить
<5–8 пунктов списком. Сухая выжимка, по которой можно освежить тему за минуту.>

## Практика
<3–5 задач по нарастающей сложности. Каждая — с условием и критерием
готовности. Без решений.>

## Вопросы для самопроверки
<5–8 вопросов. Проверяют понимание, а не память на синтаксис.>
```

### Требования к объёму

- Статья прорабатывается **за один присест: 15–25 минут теории + практика**.
- Ориентир: **400–900 слов теории**, не считая кода, практики и вопросов.
- Если тема не влезает — **дробим на части** и явно предупреждаем об этом.

### Оценка времени

Строка со временем стоит сразу под заголовком: читатель должен понимать, влезает ли занятие в сегодняшний вечер.

- **Теория** = слова ÷ 120 + минута на каждый разбираемый блок кода.
- **Практика** = прикидка на новичка, который спотыкается и лезет в документацию, а не на себя-опытного.
- Итог округляем до 5 минут вверх, честно завышая.
- **Больше 60 минут — сигнал дробить статью.** Исключение — итоговые проектные статьи, для них указывается диапазон часов.

## 3. Правила подачи

**Теория**

- Сначала «зачем», потом «как». Конструкция вводится через задачу, которую решает.
- Один новый концепт за раз. Не использовать в примерах необъяснённое; если без этого никак — одна строка пояснения и пометка «подробно в статье №N».
- **Основной приём: вводить конструкцию через ошибку компилятора или рантайма.** Сначала код без неё, затем реальный вывод. Приём проверен на курсе по Rust и работает лучше определений.
- Для Go важна вторая опора — **«почему так решили»**. Многие особенности языка (отсутствие исключений, неявные интерфейсы, минимализм) вызывают отторжение, пока не объяснён замысел.
- Проводить параллели с Python, Java, JS там, где это ускоряет понимание.
- Никаких «просто», «очевидно», «легко».

**Код**

- Go 1.26+ (локальная версия — 1.26.3). Свежие возможности отмечаются с указанием версии, в которой появились.
- **Номера версий в тексте не хардкодим**, кроме статей 01–02 (установка и инструменты) и случаев, когда возможность появилась недавно.
- Все примеры компилируются и запускаются перед публикацией. Ошибочные примеры помечаются `// ❌ не компилируется` и сопровождаются настоящим текстом ошибки — **копируется из живого вывода, не пишется по памяти**.
- Код отформатирован `gofmt` — в Go это не вопрос вкуса.
- Обработку ошибок в примерах **не опускаем**. `_ = err` в учебном коде формирует ровно ту привычку, с которой потом борются на ревью. Исключение — примеры, где обработка загромождает демонстрацию; тогда об этом пишется явно.
- Имена — по канонам Go: короткие в узкой области видимости (`i`, `r`, `buf`), осмысленные в широкой. Комментарии в коде — на русском.

**Практика**

- Задачи решаются **на стандартной библиотеке**, без внешних зависимостей (исключение — статьи про конкретные инструменты).
- Первая задача — почти по образцу. Последняя — требует комбинировать тему с предыдущими статьями.
- У каждой задачи чёткий критерий «готово».
- Решения не публикуются.

**Вопросы для самопроверки**

- Проверяют модель в голове, а не заучивание. Хорошо: «Почему этот код даёт гонку?». Плохо: «Как называется оператор для...?».
- Каждый вопрос закрыт текстом статьи.

**Язык**

- Русский. Термины — на языке оригинала с русским пояснением при первом появлении: «горутина (goroutine)».
- Не переводим то, что не переводят на практике: `slice`, `map`, `interface`, `defer`, `channel` (допустимо «канал»), `goroutine` (допустимо «горутина»).
- Обращение к читателю — на «вы», без панибратства и канцелярита.

## 4. Структура папок

```
go_materials/
├── materials_rules.md
├── 01-osnovy/
│   ├── 01-ustanovka-i-pervaya-programma.md
│   └── assets/            ← иллюстрации и схемы этой части
├── 02-sostavnye-tipy/
└── ...
```

**Правила именования**

- Папка части: `NN-nazvanie-latinicej/`.
- Файл статьи: `NN-kratkoe-nazvanie.md`, где `NN` — **сквозной номер статьи в курсе** (01–30).
- Иллюстрации: `assets/NN-chto-izobrazheno.png`, ссылка относительная.
- Только латиница, нижний регистр, дефисы.

**Иллюстрации**

- Схема добавляется, только если объясняет то, что хуже объясняется текстом: устройство слайса и его роста, планировщик горутин, дерево контекстов.
- Предпочтительны простые диаграммы (ASCII в тексте или SVG/PNG в `assets/`). Скриншоты кода — никогда.

## 5. Процесс

1. Запрос «пиши статью №N» или «пиши следующую».
2. Примеры пишутся и **прогоняются**, только потом статья.
3. Статья пишется целиком в нужный файл, статус отмечается в таблице ниже.
4. Обратная связь после проработки → правки в статью, повторяющиеся замечания → в «Журнал улучшений».

Статьи пишутся по порядку. Если тема требует опоры на непройденное — это сигнал пересмотреть порядок курса, а не тащить материал вперёд.

## 7. Правила коммитов

История коммитов — часть библиотеки: по ней должно быть видно, как курс рос и почему менялся.

**Формат сообщения**

```
<тип>(<номер статьи>): <что делает коммит>

<необязательное тело: почему так, что важно знать>
```

**Типы**

| Тип | Когда используется | Пример |
|-----|--------------------|--------|
| `article` | Новая статья | `article(03): переменные, константы и iota` |
| `edit` | Смысловая переработка готовой статьи | `edit(01): сократить раздел про историю языка` |
| `fix` | Опечатки, битые ссылки, ошибки в примерах | `fix(06): исправить вывод cap после append` |
| `assets` | Иллюстрации и схемы | `assets(06): схема устройства слайса` |
| `docs` | Правила, план курса, README | `docs: правила коммитов` |
| `chore` | Служебное: структура папок, `.gitignore` | `chore: инициализация репозитория` |

**Правила**

1. Номер статьи в скобках — **сквозной номер курса** (01–30). Без привязки к статье скобки опускаются.
2. Описание на русском, с маленькой буквы, без точки в конце, до 72 символов.
3. Описание отвечает на вопрос «что делает этот коммит», а не «что я делал».
4. **Один коммит — одна законченная единица работы.** Статья и обновление её статуса в плане идут одним коммитом.
5. Тело добавляется, когда решение неочевидно.
6. Запись в «Журнал улучшений» коммитится вместе с изменением, которое её породило.
7. В репозиторий не попадают: собранные бинарники, `.DS_Store`, временные файлы.
