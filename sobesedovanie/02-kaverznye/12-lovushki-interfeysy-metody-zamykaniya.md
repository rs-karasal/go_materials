# 12. Ловушки: интерфейсы, методы, замыкания

> ⏱ **~30 минут** на проработку · 9 задач-ловушек · грейды `[J]` `[M]` `[S]`

Вторая порция задач «что напечатает этот код». Здесь ловушки тоньше, чем со слайсами: программа делает ровно то, что написано, но написано не то, что человек имел в виду. Все выводы получены запуском.

---

### Ловушка 1: продвижение методов и «переопределение» `[M]`

```go
type Base struct{ Name string }

func (b Base) Hello() string { return "привет от " + b.Who() }
func (b Base) Who() string   { return "Base" }

type Child struct{ Base }

func (c Child) Who() string { return "Child" }

fmt.Println(Child{}.Hello())
```

**Коротко.** Печатает `привет от Base`. Метод `Hello` унаследован от `Base` и вызывает **свой** `Who`, ничего не зная про `Child`. Виртуальной диспетчеризации во встраивании нет.

**Подробно.** В Java или Python результат был бы `Child`: там метод базового класса вызвал бы переопределённый через таблицу виртуальных функций. В Go встраивание — это композиция: `Child` **содержит** `Base`, а не является им, и продвижение методов работает как синтаксический сахар над `c.Base.Hello()`. Внутри `Hello` получатель имеет тип `Base` и другого `Who` просто не видит.

**Что спросят следом.** «Как получить полиморфное поведение?» — через интерфейс: `Base` должен принимать интерфейс с методом `Who`, а не вызывать свой. «Тогда зачем встраивание?» — для переиспользования кода и композиции интерфейсов, не для иерархий.

**Красные флаги.**
- Ответ `привет от Child` — самая частая ошибка тех, кто пришёл из ООП-языков.
- Формулировка «встраивание — это наследование в Go».

### Ловушка 2: получатель-значение молча не работает `[J/M]`

```go
type Counter struct{ n int }

func (c Counter) IncVal()  { c.n++ }
func (c *Counter) IncPtr() { c.n++ }

c := Counter{}
c.IncVal()
fmt.Println(c.n)   // ?
c.IncPtr()
fmt.Println(c.n)   // ?
```

**Коротко.** Печатает `0`, затем `1`. `IncVal` получает копию структуры и увеличивает её поле — вызывающий код ничего не замечает.

**Подробно.** Самое неприятное здесь то, что синтаксис вызова одинаковый: Go сам берёт адрес для `IncPtr`, поэтому визуально методы неотличимы. Компилятор не предупреждает, линтеры по умолчанию тоже. Ошибка обнаруживается тестом — если он есть.

Отсюда правило: **не смешивайте получатели у одного типа**. Если хотя бы один метод меняет состояние, делайте указателями все.

**Что спросят следом.** «Почему тогда `c.IncPtr()` компилируется, ведь `c` не указатель?» — переменная адресуема, компилятор подставляет `(&c).IncPtr()`. «А если бы `c` был элементом карты?» — не скомпилировалось бы: элемент карты не адресуем.

**Красные флаги.**
- Ответ `1, 2`.

### Ловушка 3: `nil`-указатель в интерфейсе ошибки `[M/S]`

```go
type Err struct{ msg string }
func (e Err) Error() string { return e.msg }

func badPattern(fail bool) error {
	var e *Err
	if fail {
		e = &Err{"сломалось"}
	}
	return e          // ← здесь
}

fmt.Println(badPattern(false) == nil)
```

**Коротко.** Печатает `false`, хотя ошибки не было. Интерфейс — пара «тип, значение»: тип `*Err` заполнен, значение пусто, и такая пара не равна `nil`.

**Подробно.** Проверено рядом на правильной версии: если добавить `if e == nil { return nil }`, сравнение даёт `true`. Это самый известный подвох Go, и он не академический — так теряют часы на отладке, когда «ошибка есть, а сообщения нет».

**Что спросят следом.** «Как этого избежать?» — не объявлять переменную конкретного типа ошибки для возврата: возвращать `nil` буквально или держать переменную типа `error`. «Поможет ли `errors.Is(err, nil)`?» — нет, он тоже увидит непустой интерфейс.

**Красные флаги.**
- «Такого не бывает, `nil` есть `nil`».
- Объяснение через сборщик мусора вместо пары «тип, значение».

### Ловушка 4: сравнение интерфейсов `[M]`

```go
type Dog struct{}
func (d Dog) Sound() string { return "гав" }

var a Animal = Dog{}
var b Animal = Dog{}
fmt.Println(a == b)
```

**Коротко.** Печатает `true`. Интерфейсы равны, если совпадают динамический тип и значение; пустые структуры `Dog{}` равны между собой.

**Подробно.** Ловушка в продолжении: если внутри интерфейса окажется **несравнимый** тип — слайс, карта или функция, — сравнение вызовет панику `comparing uncomparable type` во время выполнения. Компилятор пропускает такой код, потому что содержимое интерфейса известно только в рантайме.

**Что спросят следом.** «Где это стреляет?» — сравнение ошибок оператором `==`, если внутри структура со слайсом; ключи в `map[any]T`. «Что делать?» — `errors.Is` для ошибок, `reflect.DeepEqual` для общего случая.

**Красные флаги.**
- Уверенность, что сравнение интерфейсов всегда безопасно.

### Ловушка 5: `type switch` и близкие типы `[J/M]`

```go
var i any = 5
switch i.(type) {
case int64:
	fmt.Println("int64")
case int:
	fmt.Println("int")
}
```

**Коротко.** Печатает `int`. Литерал `5` без аннотации имеет тип `int`, а не `int64`, — это разные типы, и первая ветвь не сработает.

**Подробно.** На практике ловушка вылезает при разборе JSON: числа попадают в `any` как `float64`, поэтому `v.(int)` паникует, а `case int` в `type switch` не выбирается. Ещё один вариант — работа с базой, где драйвер отдаёт `int64` независимо от размера колонки.

**Что спросят следом.** «Как обработать любое число?» — перечислить все варианты в `type switch` или привести через `reflect`. «Почему в JSON именно `float64`?» — в спецификации JSON один числовой тип, и стандартный пакет отображает его так по умолчанию.

**Красные флаги.**
- Приведение `v.(int)` для числа из разобранного JSON.

### Ловушка 6: `defer` в `main` и порядок вывода `[J]`

```go
func main() {
	defer fmt.Println("A")
	fmt.Println("B")
}
```

**Коротко.** Печатает `B`, затем `A`. Отложенный вызов срабатывает при выходе из функции, а `main` — обычная функция.

**Подробно.** Продолжение вопроса злее: если в `main` вызвать `os.Exit(1)`, отложенные вызовы **не выполнятся** — процесс завершается немедленно, минуя разматывание стека. Отсюда идиома выносить логику в `run() error`, а в `main` оставлять только обработку результата с `os.Exit`. То же касается `log.Fatal`, который внутри вызывает `os.Exit`.

**Что спросят следом.** «А при панике?» — `defer` выполняется, это гарантия языка. «Почему `log.Fatal` опасен в библиотеке?» — он убивает процесс пользователя, минуя всю уборку.

**Красные флаги.**
- Незнание, что `os.Exit` пропускает `defer`.

### Ловушка 7: вызов `nil`-функции и `nil`-метода `[M]`

```go
var fn func()
fmt.Println(fn == nil)   // true
fn()                     // ?
```

**Коротко.** Сравнение печатает `true`, а вызов даёт панику `invalid memory address or nil pointer dereference`. Функциональный тип имеет нулевое значение `nil`, и вызывать его нельзя.

**Подробно.** Интересное продолжение: метод с получателем-указателем **можно** вызвать на `nil`-указателе, и паники не будет — она случится только при обращении к полю. Этим пользуются намеренно: например, метод `String()` у `*T` может корректно обработать `nil` и вернуть `"<nil>"`. Разница в том, что метод — обычная функция с получателем-аргументом, а `nil`-функция не имеет тела вовсе.

**Что спросят следом.** «Где встречается `nil`-функция?» — необязательный колбэк в структуре конфигурации; проверять надо явно. «Как оформить необязательный колбэк?» — либо проверка `if fn != nil`, либо инициализация пустой функцией в конструкторе.

**Красные флаги.**
- Уверенность, что метод на `nil`-получателе всегда паникует.

### Ловушка 8: `%v` против `%+v` и потерянный `String()` `[J/M]`

```go
type P struct{ A int }
fmt.Printf("%v %+v\n", P{1}, P{1})
```

**Коротко.** Печатает `{1} {A:1}`. Глагол `%+v` добавляет имена полей, `%v` — нет.

**Подробно.** Продолжение злее: если у типа есть метод `String() string`, оба глагола вызовут **его**, и вы не увидите полей вообще. А если `String()` реализован с получателем-указателем, то `fmt.Println(v)` для значения его не вызовет, а `fmt.Println(&v)` вызовет — вывод одного и того же объекта будет разным.

Отдельная классика: `String()`, внутри которого вызывается `fmt.Sprintf("%v", тот же объект)` — бесконечная рекурсия и переполнение стека.

**Что спросят следом.** «Как напечатать структуру, минуя `String()`?» — привести к типу без метода или использовать `%#v`. «Что даёт `%#v`?» — синтаксис Go-литерала, удобно для отладки.

**Красные флаги.**
- Рекурсивный `String()` — встречается чаще, чем кажется.

### Ловушка 9: интерфейс с методом на указателе `[M]`

```go
type I interface{ M() }
type T struct{}
func (t *T) M() {}

m := map[string]T{"a": {}}
var _ I = m["a"]      // ?
```

**Коротко.** Не компилируется: `T does not implement I (method M has pointer receiver)`. Интерфейс реализует только `*T`, а взять адрес элемента карты нельзя.

**Подробно.** Правило: если хотя бы один метод объявлен с получателем-указателем, в набор методов `T` он не входит. Причина в адресуемости: компилятор не может гарантированно взять адрес во всех случаях — элемент карты, результат функции, значение внутри интерфейса не адресуемы.

Для переменной это работает (`var t T; var _ I = &t`), что и создаёт иллюзию, будто «иногда работает, иногда нет».

**Что спросят следом.** «Как починить?» — хранить в карте `*T` или объявить методы с получателем-значением. «Как проверить реализацию на этапе компиляции?» — идиома `var _ I = (*T)(nil)` рядом с типом.

**Красные флаги.**
- Уверенность, что набор методов у `T` и `*T` одинаковый.

## Как этим пользоваться

**Менти.** Ловушки этого раздела почти все сводятся к трём вопросам: что здесь копия, а что ссылка; какой у значения статический тип, а какой динамический; когда выполнится этот код. Научитесь задавать их себе автоматически.

**Ментор.** Ловушки 1, 2 и 3 — самые показательные: они разделяют «читал про Go» и «писал на Go». Если кандидат ошибся в первой, спросите, что будет при вызове через интерфейс, — по ответу видно, понимает ли он разницу между композицией и наследованием.
