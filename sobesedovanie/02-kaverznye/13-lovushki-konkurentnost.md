# 13. Ловушки: конкурентность

> ⏱ **~35 минут** на проработку · 10 задач-ловушек · грейды `[M]` `[S]`

Самый показательный раздел: код здесь либо зависает, либо падает, либо тихо портит данные — и всё это зависит от расписания горутин, то есть невоспроизводимо. Именно поэтому такие задачи любят давать на middle и senior. Все выводы получены запуском, часть — под `-race`.

---

### Ловушка 1: `range` по каналу без `close` `[M]`

```go
ch := make(chan int)
go func() {
	for i := range 3 {
		ch <- i
	}
	// close(ch) забыли
}()
sum := 0
for v := range ch {
	sum += v
}
```

**Коротко.** С `close` печатает `3` и завершается. Без `close` программа зависает: `range` ждёт следующего значения вечно, и рантайм сообщает `all goroutines are asleep — deadlock!`.

**Подробно.** `for range ch` завершается **только** при закрытии канала. Отсюда правило: закрывает всегда отправитель, и делает это обязательно, если получатель использует `range`. Если отправителей несколько, закрывают из отдельной горутины после `wg.Wait()` — иначе второй `close` вызовет панику.

**Что спросят следом.** «Обязательно ли закрывать канал вообще?» — нет, сборщик уберёт незакрытый; закрытие нужно только чтобы сообщить об окончании. «Что если получатель читает не через `range`?» — тогда он должен знать число сообщений сам.

**Красные флаги.**
- Закрытие канала на стороне получателя.
- «Программа просто завершится» — нет, будет тупик.

### Ловушка 2: запись в общий слайс из горутин `[M]`

```go
results := make([]int, 3)
for i := range 3 {
	wg.Add(1)
	go func() {
		defer wg.Done()
		results[i] = i * i
	}()
}
wg.Wait()
fmt.Println(results)
```

**Коротко.** Печатает `[0 1 4]`, и это **корректный** код — детектор гонок молчит. Горутины пишут по разным индексам, а разные элементы слайса — разные ячейки памяти.

**Подробно.** Ловушка здесь обратная обычной: кандидат ожидает гонку и предлагает мьютекс, хотя он не нужен. Гонка возникла бы при записи в **один** элемент, при `append` (он меняет общий дескриптор) или при чтении длины одновременно с изменением.

Отдельно: до Go 1.22 этот код был бы сломан по другой причине — переменная цикла была одна на все итерации.

**Что спросят следом.** «А если бы вместо индекса был `append`?» — гонка: `append` читает и пишет общие `len` и указатель. «Как тогда собирать результаты?» — каждая горутина в свой индекс, либо канал, либо мьютекс вокруг `append`.

**Красные флаги.**
- Предложение обернуть в мьютекс без объяснения, что именно защищаем.

### Ловушка 3: `Wait` внутри цикла `[M]`

```go
for range 3 {
	wg.Add(1)
	go func() { defer wg.Done(); time.Sleep(50 * time.Millisecond) }()
	wg.Wait()          // ← внутри цикла
}
```

**Коротко.** Занимает 150 мс вместо 50: каждая итерация ждёт свою горутину, и параллельности нет вовсе. Проверено замером.

**Подробно.** Ошибка выглядит невинно и часто появляется при рефакторинге: `Wait` переезжает внутрь цикла вместе с остальным телом. Код при этом полностью корректен — он просто медленный, поэтому ни компилятор, ни детектор гонок ничего не скажут. Обнаруживается только замером или чтением.

Та же по смыслу ошибка — `.await` в цикле в асинхронных языках и последовательные запросы там, где нужны параллельные.

**Что спросят следом.** «Где должен стоять `Wait`?» — после цикла, один раз. «Как ограничить параллелизм, если задач тысячи?» — семафор на буферизованном канале или `errgroup.SetLimit`, а не последовательный `Wait`.

**Красные флаги.**
- «Разницы нет, всё равно все три отработают» — отработают, но втрое дольше.

### Ловушка 4: `Add` внутри горутины `[M]`

```go
for range 3 {
	go func() {
		wg.Add(1)          // ← внутри
		defer wg.Done()
		work()
	}()
}
wg.Wait()
```

**Коротко.** `Wait` может завершиться мгновенно, не дождавшись ничего: если он выполнится раньше, чем горутины успеют вызвать `Add`, счётчик будет нулевым.

**Подробно.** Поведение зависит от расписания, поэтому на слабой нагрузке код «работает», а под нагрузкой или на другой машине начинает пропускать задачи. `Add` всегда вызывают **до** `go`, в той же горутине, что и `Wait`.

Родственная ошибка — передача `WaitGroup` по значению: копия имеет свой счётчик, и `Wait` зависает навсегда. Её, в отличие от первой, ловит `go vet`.

**Что спросят следом.** «Почему `Done` пишут через `defer`?» — чтобы сработал при панике и любом `return`. «Что будет при лишнем `Done`?» — паника `negative WaitGroup counter`.

**Красные флаги.**
- Незнание, что `Add` до `go` — обязательное требование, а не стилистика.

### Ловушка 5: двойное закрытие канала `[M]`

```go
for range 3 {
	go func() { close(done) }()
}
```

**Коротко.** Паника `close of closed channel` у второй горутины. Закрыть канал можно ровно один раз.

**Подробно.** Правильное решение — `sync.Once`:

```go
var once sync.Once
go func() { once.Do(func() { close(done) }) }()
```

Проверено: три горутины, паники нет. Второй вариант — назначить единственного ответственного за закрытие, обычно ту горутину, что ждёт остальных через `wg.Wait()`.

**Что спросят следом.** «Что ещё паникует?» — отправка в закрытый канал и закрытие `nil`-канала. «А чтение из закрытого?» — безопасно: отдаёт оставшиеся значения, затем нулевое с `ok == false`.

**Красные флаги.**
- Проверка `if !closed { close(ch) }` через флаг — сама по себе гонка.

### Ловушка 6: `select` без `default` на пустых каналах `[M]`

```go
select {
case v := <-ch1:
	use(v)
case v := <-ch2:
	use(v)
}
```

**Коротко.** Если ни один канал не готов, `select` блокируется навсегда. Если оба готовы — выбор **случаен**, а не сверху вниз.

**Подробно.** Случайность — защита от голодания, но она означает, что нельзя рассчитывать на приоритет: «сначала проверим отмену, потом данные» не работает. Если отмена должна иметь приоритет, её проверяют отдельным неблокирующим `select` перед основным.

Отдельная ловушка — `default` внутри цикла без паузы: получается busy-loop, сжигающий ядро вхолостую.

**Что спросят следом.** «Как сделать таймаут?» — ветвь `case <-time.After(d)`; проверено, срабатывает корректно. «Что делает ветвь с `nil`-каналом?» — никогда не выбирается; так ветви отключают динамически.

**Красные флаги.**
- Уверенность, что ветви проверяются по порядку.

### Ловушка 7: `break` внутри `select` `[M]`

```go
for {
	select {
	case <-done:
		break        // ← выходит из select, не из цикла
	case v := <-ch:
		use(v)
	}
}
```

**Коротко.** `break` выходит из `select`, а цикл продолжается — получается бесконечный цикл, который выглядит корректным. Нужна метка: `break loop`.

**Подробно.** Ошибка молчаливая: компилятор не возражает, поведение просто неверное. Альтернатива метке — `return`, если весь смысл функции в этом цикле. Та же ловушка есть с `break` внутри `switch` внутри цикла.

**Что спросят следом.** «Как выйти из вложенных циклов?» — метка перед внешним циклом, работает и с `continue`. «Что ещё забывают в главном цикле?» — `ticker.Stop()` через `defer`, иначе тикер продолжает работать.

**Красные флаги.**
- Ответ «выйдет из цикла».

### Ловушка 8: горутина захватывает мьютекс и паникует `[S]`

```go
mu.Lock()
doWork()       // паникует
mu.Unlock()    // не выполнится
```

**Коротко.** Мьютекс останется захваченным навсегда, и все остальные горутины зависнут на `Lock`. В Go нет «отравления» мьютекса, как в Rust, — просто вечная блокировка.

**Подробно.** Лечится единственным способом: `defer mu.Unlock()` сразу после `Lock`. Отложенный вызов выполняется при разматывании стека, поэтому замок освободится даже при панике.

Продолжение: если паника произошла в горутине без `recover`, программа всё равно завершится целиком — но в сервисе с восстановлением на границе обработчика этот сценарий вполне реален, и тогда сервис живёт с намертво захваченным замком.

**Что спросят следом.** «Почему `sync.Mutex` не рекурсивный?» — авторы считают, что потребность в рекурсивном захвате означает проблему в дизайне. «Как найти зависший замок?» — `Ctrl+\` печатает стеки всех горутин с указанием, чего каждая ждёт.

**Красные флаги.**
- `Unlock` в конце функции без `defer`.

### Ловушка 9: контекст, который никто не отменяет `[M]`

```go
ctx, _ := context.WithTimeout(context.Background(), time.Second)
doWork(ctx)
```

**Коротко.** Отброшенный `cancel` — утечка: контекст с таймаутом заводит таймер и регистрируется у родителя, и эти ресурсы живут до срабатывания таймаута, даже если работа давно закончилась. Ловится `go vet`.

**Подробно.** Пишут всегда `defer cancel()` сразу после создания; повторный вызов безопасен, так что перестраховаться нельзя. На одном вызове это незаметно, но в обработчике, выполняющемся тысячи раз в секунду, таймеры накапливаются.

**Что спросят следом.** «Что будет, если передать `nil` вместо контекста?» — паника при первом обращении; используют `context.Background()` или `context.TODO()`. «Отменяет ли отмена потомка родителя?» — нет, только сверху вниз.

**Красные флаги.**
- Игнорирование `cancel` через `_` как привычка.

### Ловушка 10: `time.After` в цикле `[S]`

```go
for {
	select {
	case v := <-ch:
		use(v)
	case <-time.After(time.Minute):
		return
	}
}
```

**Коротко.** На каждой итерации создаётся новый таймер, который живёт до срабатывания — то есть минуту. При частых сообщениях таймеры накапливаются и съедают память.

**Подробно.** Правильно — создать `time.NewTimer` один раз до цикла и сбрасывать его через `Reset`, либо использовать контекст с дедлайном. Оговорка: сброс таймера требует аккуратности, если он уже сработал, поэтому в реальном коде чаще берут контекст.

Отдельно про `time.Ticker`: его обязательно останавливать через `defer ticker.Stop()`, иначе он продолжает тикать и удерживать ресурсы.

**Что спросят следом.** «Как это заметить?» — рост потребления памяти при неизменной нагрузке; профиль `heap` покажет таймеры. «Когда `time.After` уместен?» — в разовых операциях, не в горячем цикле.

**Красные флаги.**
- Уверенность, что таймер собирается сразу после выхода из `select`.

## Как этим пользоваться

**Менти.** Задавайте себе четыре вопроса на каждый конкурентный фрагмент: кто закрывает канал; кто ждёт завершения и где; что здесь общее между горутинами; есть ли у каждой горутины путь выхода. Большинство ловушек этого раздела отвечают на один из них.

**Ментор.** Ловушки 3 и 4 хорошо отделяют тех, кто писал конкурентный код, от тех, кто читал про него: обе не дают ни ошибки компиляции, ни срабатывания детектора гонок — только неверное поведение. Ловушку 8 стоит давать на senior вместе с вопросом «как вы это обнаружите в проде».
