# 04. Ошибки, `panic`, `defer`

> ⏱ **~30 минут** на проработку · 12 разборов · грейды `[J]` `[M]` `[S]`

Обработка ошибок — то, за что Go критикуют и о чём спрашивают почти всегда. Вопросы простые на вид, но легко провалиться на `defer` с именованным результатом и на разнице между `%w` и `%v`. Подробное изложение — в курсе (`kurs/`), статьи 05, 13, 14.

---

### Почему в Go нет исключений? `[J]`

**Коротко.** Ошибка — обычное значение, возвращаемое наравне с результатом. Это даёт три вещи: ошибка видна в сигнатуре, нет невидимых путей выхода из функции, и её нельзя молча пропустить. Плата — многословность.

**Подробно.** В языке с исключениями любая строка может прервать выполнение, и понять это можно только из документации. В Go выход всегда явный, код читается сверху вниз. Компилятор не даст объявить `err` и не использовать его, так что «забыть» ошибку сложнее, чем кажется.

**Что спросят следом.** «Что вас раздражает в этом подходе?» — честный ответ про три строки проверки на каждый вызов ценится больше, чем отрицание проблемы. «Как с этим живут?» — оборачивание с контекстом плюс `errors.Is`/`As`, чтобы проверка была не механической.

**Красные флаги.**
- «Исключения хуже, потому что медленные» — дело не в скорости, а в видимости путей выполнения.

---

### Что такое `error` с точки зрения системы типов? `[J]`

**Коротко.** Обычный интерфейс с одним методом `Error() string`. Любой тип с таким методом является ошибкой; `nil` означает успех.

**Подробно.** Отсюда следует, что ошибка может нести данные: структура с полями «поле», «причина», «код ответа». Метод `Error()` объявляют на указателе — это соглашение, благодаря которому две ошибки с одинаковым содержимым остаются разными значениями.

**Что спросят следом.** «Как отличить один вид ошибки от другого?» — сторожевые значения (`ErrNotFound`) плюс `errors.Is`, либо свой тип плюс `errors.As`. «Почему сообщения пишут с маленькой буквы и без точки?» — они склеиваются в цепочку при оборачивании.

**Красные флаги.**
- Уверенность, что `error` — встроенный особый тип, а не интерфейс.

### В чём разница между `%w` и `%v` в `fmt.Errorf`? `[M]`

**Коротко.** `%w` оборачивает ошибку, сохраняя её внутри и оставляя доступной для `errors.Is` и `errors.As`. `%v` просто вставляет текст, и связь с исходной ошибкой теряется.

**Подробно.** Проверено живьём:

```
Is через два слоя (%w): true
Is после %v:            false
```

Оборачивать можно многократно — `errors.Is` разворачивает всю цепочку. Единственная причина сознательно использовать `%v` — намеренно скрыть внутреннюю ошибку, чтобы она не стала частью публичного контракта вашего пакета.

**Что спросят следом.** «Сколько ошибок можно обернуть одним `Errorf`?» — с Go 1.20 несколько `%w` в одной строке, плюс есть `errors.Join`. «Что писать в тексте обёртки?» — что делали, а не что случилось: «чтение конфигурации», а не «ошибка чтения».

**Красные флаги.**
- Использование `%v` по привычке с последующим удивлением, почему `errors.Is` не срабатывает.

### Почему `err == ErrNotFound` — ненадёжная проверка? `[M]`

**Коротко.** Потому что любой промежуточный слой мог обернуть ошибку, и прямое сравнение перестанет работать. `errors.Is` разворачивает цепочку и сравнивает на каждом уровне.

**Подробно.** Это тот случай, когда код «работает», пока кто-то не добавит контекст в середине стека, — и ломается молча, без ошибки компиляции. Правило простое: **сравнивайте ошибки только через `errors.Is`**, даже если сейчас обёртки нет. То же касается `sql.ErrNoRows`, `io.EOF`, `os.ErrNotExist`.

**Что спросят следом.** «Когда нужен `errors.As` вместо `Is`?» — когда нужны данные из ошибки: `As` находит в цепочке ошибку нужного типа и записывает её в переменную. «Почему `As` принимает указатель на указатель?» — потому что он присваивает значение в переданную переменную.

**Красные флаги.**
- Проверка ошибки по тексту через `strings.Contains(err.Error(), ...)`.

### Когда уместна паника, а когда `error`? `[M]`

**Коротко.** Паника — про ошибку программиста: нарушен инвариант, состояние невозможно. `error` — про ситуацию среды: файла нет, сеть недоступна, ввод неверен. Критерий: может ли вызывающий код осмысленно отреагировать.

**Подробно.** Три законных случая для паники: невозможное состояние в `default` ветке `switch`; функции `Must...`, вызываемые на инициализации с заведомо корректными данными (`regexp.MustCompile`); критичная инициализация, без которой сервис не должен стартовать. **В библиотечном коде паниковать нельзя** — это отбирает у пользователя право решать.

**Что спросят следом.** «Что делает паника с программой?» — разматывает стек, выполняя `defer`, и завершает процесс с ненулевым кодом. «Выполнится ли `defer` при панике?» — да, именно поэтому освобождение ресурсов через `defer` надёжно.

**Красные флаги.**
- Использование паники как замены исключениям для управления потоком.

### Что напечатает этот код? `[M]`

```go
func namedResult() (result int) {
	defer func() { result *= 2 }()
	return 5
}
```

**Коротко.** `10`. `return 5` сначала присваивает 5 именованному результату, затем выполняется `defer`, который его удваивает, и только потом функция возвращает управление.

**Подробно.** Ключ в том, что `return` в Go — не одна операция: сначала запись в результат, потом отложенные вызовы, потом выход. С обычным (неименованным) результатом это не работает:

```go
func plainResult() int {
	r := 5
	defer func() { r *= 2 }()
	return r     // 5
}
```

Здесь значение уже скопировано в результат, и `defer` меняет локальную переменную впустую. Проверено: `10` и `5` соответственно.

**Что спросят следом.** «Где это применяют на практике?» — чтобы вернуть ошибку закрытия файла или откатить транзакцию в `defer`, не теряя основную ошибку. «Почему тогда именованные результаты не используют везде?» — «голый» `return` в длинной функции читается плохо.

**Красные флаги.**
- Ответ «5» для первого случая — самый частый провал на этом вопросе.

### В каком порядке выполняются `defer` и когда вычисляются их аргументы? `[J/M]`

**Коротко.** В обратном порядке объявления, как стек. Аргументы вычисляются **в момент объявления** `defer`, а не выполнения.

**Подробно.** Проверено:

```
порядок defer: 2 1 0
аргумент вычислен при объявлении: 1   (хотя x стал 100)
```

Обратный порядок логичен: если открыли файл, потом соединение — закрывать надо в обратной последовательности. Раннее вычисление аргументов — источник недоумения: чтобы взять актуальное значение, оборачивайте в замыкание `defer func() { fmt.Println(x) }()`.

**Что спросят следом.** «Что если `defer` внутри цикла?» — он привязан к функции, а не к блоку, поэтому все вызовы накопятся до конца функции; цикл, открывающий файлы, будет держать их все. «Как чинить?» — вынести тело цикла в отдельную функцию.

**Красные флаги.**
- Уверенность, что `defer` срабатывает в конце блока `{}`.

### Как `recover` превращает панику в ошибку? `[M]`

**Коротко.** `recover` работает только внутри `defer`. Он останавливает разматывание стека и возвращает значение, переданное в `panic`. В связке с именованным результатом это позволяет вернуть ошибку вместо падения.

**Подробно.**

```go
func recoverValue() (err error) {
	defer func() {
		if r := recover(); r != nil {
			err = fmt.Errorf("поймали: %v", r)
		}
	}()
	panic("бум")
}
```

Возвращает `поймали: бум`. Аргумент паники имеет тип `any`, поэтому его обычно разбирают: если паниковали ошибкой, тип сохраняется и `errors.Is` продолжает работать.

**Что спросят следом.** «Где `recover` действительно нужен?» — на границе HTTP-обработчика, на публичной границе библиотеки, в долгоживущих воркерах. «Чего делать не надо?» — заворачивать каждую функцию «на всякий случай»: это прячет баги.

**Красные флаги.**
- Вызов `recover()` вне `defer` — он вернёт `nil` и ничего не сделает.

### Почему `recover` не ловит панику из другой горутины? `[S]`

**Коротко.** Потому что `recover` работает со стеком своей горутины. Паника в любой горутине без собственного `recover` завершает **всю программу**, и обработчик в `main` не поможет.

**Подробно.** Это принципиально отличается от исключений в языках с потоками, где необработанное исключение обычно убивает только поток. Практическое следствие: каждая долгоживущая горутина, выполняющая внешний или ненадёжный код, должна иметь свой `defer` с `recover`. Пул воркеров без такой защиты падает целиком из-за одной некорректной задачи.

**Что спросят следом.** «Как это правильно оформить?» — обёртка `safeGo(fn)`, которая запускает горутину с `recover` и логированием. «Что делать с пойманной паникой?» — залогировать со стеком (`debug.Stack()`) и решить: продолжить или остановить воркер.

**Красные флаги.**
- Уверенность, что паника в горутине «просто убьёт горутину».

### Что вернёт `recover()`, если паниковали значением `nil`? `[S]`

**Коротко.** С Go 1.21 — специальное значение с текстом `panic called with nil argument`. Раньше `recover()` возвращал `nil`, и отличить «паники не было» от «паника с `nil`» было невозможно.

**Подробно.** Проверено на актуальной версии:

```
recover вернул: panic called with nil argument
```

Изменение сделали именно потому, что старое поведение маскировало реальные паники: проверка `if r := recover(); r != nil` пропускала такой случай, и программа продолжала работать в сломанном состоянии. Вопрос уровня `[S]` и задают его редко — но он показывает, следит ли человек за изменениями языка.

**Что спросят следом.** «Как вернуть старое поведение?» — переменной окружения `GODEBUG=panicnil=1`; нужно только для совместимости со старым кодом.

**Красные флаги.**
- Уверенность, что `panic(nil)` невозможен.

### Что не так с конструкцией «залогировать и вернуть ошибку»? `[M]`

**Коротко.** Одна ошибка попадает в лог столько раз, сколько уровней она прошла. Правило: **либо обработали, либо вернули** — логирует тот, кто принимает решение, обычно верхний уровень.

**Подробно.** Промежуточные слои должны добавлять контекст через `%w`, а не писать в лог. Тогда наверху получается одна запись с полной цепочкой: «обработка запроса: чтение конфигурации: open config.toml: no such file or directory». Дублирующиеся записи — типичное замечание на ревью и признак, что человек переносит привычки из языков с исключениями.

**Что спросят следом.** «А если ошибка не критична и обрабатывается на месте?» — тогда логируем и не возвращаем: это и есть «обработали». «Что писать в лог?» — структурную запись с полями, включая идентификатор запроса.

**Красные флаги.**
- `log.Println(err); return err` как привычный шаблон.

### Как правильно обработать ошибку закрытия ресурса? `[S]`

**Коротко.** `defer f.Close()` теряет ошибку. Если запись важна — данные могли не долететь до диска — ошибку закрытия возвращают через именованный результат, не затирая основную.

**Подробно.**

```go
func write(name string) (err error) {
	f, err := os.Create(name)
	if err != nil {
		return err
	}
	defer func() {
		if cerr := f.Close(); cerr != nil && err == nil {
			err = cerr
		}
	}()
	_, err = f.WriteString("данные")
	return err
}
```

Условие `err == nil` важно: если основная операция уже сломалась, её ошибка информативнее. Для файлов, открытых только на чтение, так заморачиваться не нужно — там `defer f.Close()` достаточно.

**Что спросят следом.** «Где ещё та же проблема?» — откат транзакции в базе, закрытие тела HTTP-ответа. «Как это проверяет линтер?» — `errcheck` находит проигнорированные ошибки, включая `Close`.

**Красные флаги.**
- Уверенность, что `Close` не может вернуть значимую ошибку.
