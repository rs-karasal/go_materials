# 16. Задачи на конкурентность

> ⏱ **~90 минут** на проработку · 5 задач по 20–25 минут · грейды `[M]` `[S]`

Главная секция live-coding для Go: здесь проверяют то, ради чего язык и выбирают. Задачи почти всегда одни и те же — пул воркеров, конвейер, ограничение параллелизма, — но интервьюер смотрит на детали: отмену, закрытие каналов, отсутствие утечек.

Все решения проверены под `-race`: гонок нет, `go vet` и `gofmt` чисты.

---

## Что проверяют в этой секции

Помимо работающего кода, четыре вещи:

1. **Кто закрывает каналы и когда.** Самая частая ошибка — закрытие получателем или отсутствие закрытия вовсе.
2. **Есть ли у каждой горутины путь выхода.** Отмена через контекст, а не только «дойдёт до конца».
3. **Ограничен ли параллелизм.** Запуск горутины на каждую задачу без предела — красный флаг.
4. **Как собираются ошибки.** Первая ошибка, все ошибки или игнорирование.

Кандидат, который сам проговаривает «здесь возможна утечка, поэтому добавлю `select` с `ctx.Done()`», выигрывает у того, кто пишет молча.

### Задача 1: пул воркеров с ограничением и отменой `[M]` · ~25 мин

**Условие.** Обработать слайс задач фиксированным числом горутин, собрать результаты в исходном порядке, поддержать отмену через контекст и вернуть первую ошибку.

**На что смотрит интервьюер.**

- Число горутин фиксировано, а не по одной на задачу.
- Порядок результатов сохранён — обычно через индекс, а не через порядок получения.
- Канал задач закрывает отправитель, канал результатов — отдельная горутина после `wg.Wait()`.
- Каждая отправка в канал обёрнута в `select` с `ctx.Done()`, иначе при отмене горутина зависнет.

**Решение.**

```go
func WorkerPool(ctx context.Context, jobs []int, workers int,
	do func(context.Context, int) (int, error)) ([]int, error) {

	type res struct {
		idx int
		val int
		err error
	}
	jobCh := make(chan int)
	resCh := make(chan res)

	var wg sync.WaitGroup
	for range workers {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for idx := range jobCh {
				v, err := do(ctx, jobs[idx])
				select {
				case resCh <- res{idx, v, err}:
				case <-ctx.Done():
					return
				}
			}
		}()
	}

	go func() {
		defer close(jobCh)
		for i := range jobs {
			select {
			case jobCh <- i:
			case <-ctx.Done():
				return
			}
		}
	}()

	go func() { wg.Wait(); close(resCh) }()

	out := make([]int, len(jobs))
	var firstErr error
	for r := range resCh {
		if r.err != nil && firstErr == nil {
			firstErr = r.err
		}
		out[r.idx] = r.val
	}
	return out, firstErr
}
```

Проверено: пять задач на трёх воркерах дали `[1 4 9 16 25]` — порядок сохранён; при падении второй задачи вернулась её ошибка.

Разберите три горутины отдельно: воркеры читают из `jobCh`, отдельная горутина наполняет его и закрывает, ещё одна ждёт всех воркеров и закрывает `resCh`. Без последней главный цикл `for r := range resCh` завис бы навсегда.

**Типичные ошибки.**

- Закрытие `resCh` в одном из воркеров — паника при повторном закрытии.
- Отправка в `resCh` без `select` — при отмене воркер зависает, получатель уже ушёл.
- Сбор результатов в слайс через `append` из горутин — гонка и потерянный порядок.
- Отсутствие `close(jobCh)` — воркеры не завершатся, `wg.Wait()` не вернётся.

**Развитие.** «Как остановить остальных при первой ошибке?» — `errgroup.WithContext`: он отменит контекст, и воркеры выйдут по `ctx.Done()`. «Как ограничить время всей операции?» — `context.WithTimeout` на входе.

### Задача 2: fan-in нескольких каналов `[M]` · ~20 мин

**Условие.** Слить несколько входных каналов в один выходной. Выходной канал закрывается, когда закрылись все входные.

**На что смотрит интервьюер.**

- По горутине на входной канал плюс `WaitGroup`.
- Закрытие выходного канала **после** завершения всех — из отдельной горутины.
- Отправка через `select` с контекстом, иначе при отказе получателя горутины зависнут.
- Использование дженериков вместо `any`.

**Решение.**

```go
func FanIn[T any](ctx context.Context, chans ...<-chan T) <-chan T {
	out := make(chan T)
	var wg sync.WaitGroup
	for _, c := range chans {
		wg.Add(1)
		go func(c <-chan T) {
			defer wg.Done()
			for v := range c {
				select {
				case out <- v:
				case <-ctx.Done():
					return
				}
			}
		}(c)
	}
	go func() { wg.Wait(); close(out) }()
	return out
}
```

Проверено: два канала по два значения дали сумму 10.

Возвращаемый тип `<-chan T` — только для чтения: так вызывающий код не сможет случайно записать в канал или закрыть его. Это дешёвая документация, и её отсутствие интервьюер замечает.

**Типичные ошибки.**

- `close(out)` внутри цикла или в одной из горутин.
- Забытый `wg.Wait()` перед закрытием — паника отправки в закрытый канал.
- Возврат двустороннего канала.
- Отсутствие `select` при отправке — классическая утечка, если получатель перестал читать.

**Развитие.** «Как сделать fan-out?» — несколько горутин читают из одного канала, распределение делает рантайм. «Как построить конвейер?» — каждая стадия принимает входной канал и возвращает выходной, закрывая его по завершении.

### Задача 3: семафор для ограничения параллелизма `[M]` · ~15 мин

**Условие.** Ограничить число одновременных обращений к внешнему сервису заданным числом, с поддержкой отмены.

**На что смотрит интервьюер.**

- Знает ли идиому «буферизованный канал как семафор».
- Освобождает ли слот через `defer` — иначе паника оставит его занятым навсегда.
- Поддерживает ли отмену при ожидании слота.

**Решение.**

```go
type Semaphore chan struct{}

func (s Semaphore) Acquire(ctx context.Context) error {
	select {
	case s <- struct{}{}:
		return nil
	case <-ctx.Done():
		return ctx.Err()
	}
}

func (s Semaphore) Release() { <-s }
```

Использование:

```go
sem := make(Semaphore, 2)
if err := sem.Acquire(ctx); err != nil {
	return err
}
defer sem.Release()
```

Проверено: десять горутин при ёмкости 2 дали максимум два одновременно активных — счётчик под мьютексом это подтвердил.

**Типичные ошибки.**

- `Release` без `defer`.
- Ожидание слота без контекста — горутина зависает, если работа отменена.
- Тип канала `bool` вместо `struct{}` — лишний байт на слот.
- Захват семафора **после** запуска горутины: тогда десять тысяч горутин уже созданы и ждут.

**Развитие.** «Чем это отличается от пула воркеров?» — семафор ограничивает параллелизм, но горутины всё равно создаются на каждую задачу; пул создаёт их фиксированное число. «Что в стандартных библиотеках?» — `golang.org/x/sync/semaphore` с взвешенными слотами, `errgroup.SetLimit`.

### Задача 4: конвейер с отменой `[M/S]` · ~25 мин

**Условие.** Построить цепочку стадий: генератор чисел → возведение в квадрат → фильтр чётных. Каждая стадия — горутина, связь через каналы, вся цепочка отменяется контекстом.

**На что смотрит интервьюер.**

- Каждая стадия закрывает **свой** выходной канал через `defer close(out)`.
- Отправка обёрнута в `select` с контекстом — иначе при отмене стадия зависнет на отправке.
- Стадии соединяются композицией, а не одной функцией с тремя циклами.

**Форма стадии.**

```go
func Square(ctx context.Context, in <-chan int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for v := range in {
			select {
			case out <- v * v:
			case <-ctx.Done():
				return
			}
		}
	}()
	return out
}
```

Каждая стадия выглядит одинаково: создать выходной канал, запустить горутину, вернуть канал сразу. Соединение читается как формулировка задачи:

```go
res := Filter(ctx, Square(ctx, Gen(ctx, 1, 2, 3, 4)))
```

**Типичные ошибки.**

- Закрытие входного канала вместо выходного.
- Отсутствие `defer close(out)` — потребитель зависает на `range`.
- Отправка без `select` — при досрочном выходе потребителя вся цепочка утекает.
- Возврат канала после завершения работы вместо немедленного — теряется потоковость.

**Развитие.** «Как узнать, что стадия — узкое место?» — буферизовать каналы и смотреть, где скапливается; профилировать. «Как распараллелить одну стадию?» — fan-out на несколько горутин с последующим fan-in.

### Задача 5: конкурентная карта с истечением срока `[S]` · ~25 мин

**Условие.** Кеш с временем жизни записей, безопасный для конкурентного доступа. Устаревшие записи не должны накапливаться.

**На что смотрит интервьюер.**

- Выбор между ленивым удалением при обращении и фоновой уборкой — и понимание компромисса.
- Корректная остановка фоновой горутины: без неё кеш живёт вечно после того, как стал не нужен.
- Использование `RWMutex` осознанно, а не по привычке.
- Понимание, что `time.Now()` под замком — источник конкуренции.

**Ключевые решения, которые надо проговорить.**

Ленивое удаление проще: при `Get` проверяем метку времени и удаляем просроченное. Проблема — записи, к которым никто не обращается, остаются навсегда, и кеш растёт. Фоновая уборка тикером решает это, но добавляет горутину, которую надо останавливать, и периодический проход по всей карте под замком.

Практичный компромисс — оба механизма: ленивая проверка при чтении плюс редкая фоновая уборка. Остановку оформляют методом `Close()`, закрывающим канал `done`, — и обязательно предупреждают пользователя, что его надо вызвать.

**Типичные ошибки.**

- Фоновая горутина без способа остановки — утечка на каждый созданный кеш.
- Уборка всей карты под `Lock` на большом объёме — заметная пауза для всех.
- `RWMutex` там, где `Get` тоже пишет (например, обновляет время доступа).
- Отсутствие ограничения размера — кеш растёт до OOM.

**Развитие.** «Как ограничить размер?» — вытеснение по LRU из прошлой темы, то есть связка карта плюс список. «Как избежать лавины при истечении?» — разброс времени жизни и `singleflight`, чтобы за пропущенным ключом пошёл один запрос, а не сотня.

## Чек-лист перед секцией

Соберите из головы, не подглядывая:

- пул воркеров с сохранением порядка результатов и отменой;
- fan-in с корректным закрытием выходного канала;
- семафор на буферизованном канале с `defer Release`;
- стадия конвейера — шаблон из пяти строк;
- ответ на вопрос «где здесь может утечь горутина» для любого своего кода.

Главное правило секции: **проговаривайте, кто закрывает канал и как выходит каждая горутина**. Это ровно те две вещи, из-за которых конкурентный код ломается в проде.
