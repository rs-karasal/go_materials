# 15. Задачи уровня middle

> ⏱ **~75 минут** на проработку · 5 задач по 15–20 минут · грейд `[M]`

На middle задачи перестают быть про синтаксис и становятся про проектирование: интервьюер смотрит, как человек выбирает структуры данных, где ставит границы ответственности и как обрабатывает ошибки. Часто просят не дописать до конца, а объяснить компромиссы.

Все решения проверены: компилируются, проходят `go vet` и `gofmt`.

### Задача 1: LRU-кеш `[M]` · ~20 мин

**Условие.** Реализуйте кеш фиксированного размера с вытеснением наименее недавно использованного элемента. Операции `Get` и `Put` за O(1).

**На что смотрит интервьюер.**

- Догадается ли до связки «карта плюс двусвязный список» — это ключ к O(1).
- Обновляет ли позицию элемента при `Get`, а не только при `Put`.
- Удаляет ли ключ из карты при вытеснении — забыть это значит устроить утечку.
- Вспомнит ли про `container/list` в стандартной библиотеке.
- Спросит ли про потокобезопасность.

**Решение.**

```go
type entry struct {
	key string
	val int
}

type LRU struct {
	cap   int
	ll    *list.List
	items map[string]*list.Element
}

func NewLRU(capacity int) *LRU {
	return &LRU{cap: capacity, ll: list.New(), items: make(map[string]*list.Element, capacity)}
}

func (c *LRU) Get(k string) (int, bool) {
	el, ok := c.items[k]
	if !ok {
		return 0, false
	}
	c.ll.MoveToFront(el)
	return el.Value.(*entry).val, true
}

func (c *LRU) Put(k string, v int) {
	if el, ok := c.items[k]; ok {
		c.ll.MoveToFront(el)
		el.Value.(*entry).val = v
		return
	}
	el := c.ll.PushFront(&entry{k, v})
	c.items[k] = el
	if c.ll.Len() > c.cap {
		last := c.ll.Back()
		c.ll.Remove(last)
		delete(c.items, last.Value.(*entry).key)
	}
}
```

Проверено на кеше размера 2: после `Put(a)`, `Put(b)`, `Get(a)`, `Put(c)` вытеснен именно `b`, а `a` остался — то есть `Get` действительно обновил позицию.

Обратите внимание: в элементе списка хранится **и ключ, и значение**. Без ключа при вытеснении невозможно узнать, что удалять из карты.

**Типичные ошибки.**

- `Get` не двигает элемент в начало — тогда это не LRU.
- Вытеснение из списка без удаления из карты — карта растёт бесконечно.
- Хранение в списке только значения.
- Обход списка для поиска — O(n) вместо O(1).

**Развитие.** «Сделайте потокобезопасным» — мьютекс на всю структуру; `RWMutex` не поможет, потому что `Get` тоже пишет (двигает элемент). «Как добавить время жизни?» — поле с меткой времени и ленивое удаление при обращении либо фоновая уборка.

### Задача 2: обёртка над `io.Reader` со счётчиком `[M]` · ~15 мин

**Условие.** Напишите тип, который оборачивает `io.Reader` и считает прочитанные байты.

**На что смотрит интервьюер.**

- Понимает ли, что достаточно реализовать один метод, и тип встанет на место любого `Reader`.
- Правильно ли пробрасывает ошибку и число прочитанных байт.
- Знает ли, что `Read` может вернуть данные **вместе** с `io.EOF`.
- Догадается ли, что это и есть идиома декоратора в Go.

**Решение.**

```go
type CountingReader struct {
	r io.Reader
	N int64
}

func (cr *CountingReader) Read(p []byte) (int, error) {
	n, err := cr.r.Read(p)
	cr.N += int64(n)
	return n, err
}
```

Проверено: `io.Copy(io.Discard, cr)` на строке «привет мир» даёт 19 байт — кириллица по два байта, пробел один.

Ключевая деталь: счётчик увеличивается **до** проверки ошибки, потому что байты могли быть прочитаны и при `io.EOF`. Это самое частое место, где ошибаются.

**Типичные ошибки.**

- `if err != nil { return 0, err }` до увеличения счётчика — теряются последние байты.
- Возврат собственного числа вместо `n` от вложенного читателя.
- Получатель-значение — счётчик не будет расти.
- Попытка прочитать всё в буфер внутри `Read`.

**Развитие.** «Добавьте ограничение объёма» — вернуть ошибку при превышении; в стандартной библиотеке это `io.LimitReader`. «Зачем это нужно?» — защита от бесконечного тела запроса: читать внешние данные без лимита нельзя.

### Задача 3: повтор с экспоненциальной задержкой `[M]` · ~20 мин

**Условие.** Напишите функцию, повторяющую операцию при ошибке: заданное число попыток, удваивающаяся задержка, поддержка отмены через контекст, различение временных и постоянных ошибок.

**На что смотрит интервьюер.**

- Использует ли `select` с `ctx.Done()` вместо `time.Sleep` — со `Sleep` отмена не работает.
- Различает ли ошибки, которые нет смысла повторять.
- Не делает ли лишнюю задержку после последней попытки.
- Оборачивает ли итоговую ошибку с контекстом.

**Решение.**

```go
var ErrPermanent = errors.New("постоянная ошибка")

func Retry(ctx context.Context, attempts int, base time.Duration, fn func() error) error {
	var last error
	delay := base
	for i := range attempts {
		last = fn()
		if last == nil {
			return nil
		}
		if errors.Is(last, ErrPermanent) {
			return last
		}
		if i == attempts-1 {
			break
		}
		select {
		case <-ctx.Done():
			return errors.Join(last, ctx.Err())
		case <-time.After(delay):
		}
		delay *= 2
	}
	return fmt.Errorf("после %d попыток: %w", attempts, last)
}
```

Проверено: операция, успешная с третьего раза, отработала за три попытки; операция с постоянной ошибкой — за одну.

**Типичные ошибки.**

- `time.Sleep` вместо `select` — контекст перестаёт работать, отмена не доходит.
- Задержка после последней попытки — лишнее ожидание перед возвратом ошибки.
- Повтор всех ошибок подряд, включая 400 Bad Request.
- Потеря исходной ошибки: возвращается только «превышено число попыток».

**Развитие.** «Что добавить в проде?» — джиттер, случайный разброс задержки: без него все клиенты после сбоя ретраят синхронно и добивают сервис. «Что ещё?» — потолок задержки и общий бюджет времени. «Как это связано с circuit breaker?» — ретраи лечат единичные сбои, размыкатель — длительную недоступность.

### Задача 4: группировка по ключу `[M]` · ~12 мин

**Условие.** Напишите обобщённую функцию, группирующую слайс по ключу, вычисляемому функцией.

**На что смотрит интервьюер.**

- Владеет ли дженериками и ограничением `comparable`.
- Знает ли, что `append` к отсутствующему ключу карты работает: нулевое значение слайса — `nil`, и `append` его инициализирует.
- Не пишет ли лишнюю проверку существования ключа.

**Решение.**

```go
func GroupBy[T any, K comparable](in []T, key func(T) K) map[K][]T {
	out := make(map[K][]T)
	for _, v := range in {
		k := key(v)
		out[k] = append(out[k], v)
	}
	return out
}
```

Проверено на трёх пользователях: по Алматы два, по Астане один.

Строка `out[k] = append(out[k], v)` — идиома, которую стоит знать: обращение к отсутствующему ключу даёт `nil`-слайс, `append` создаёт новый, присваивание кладёт его в карту.

**Типичные ошибки.**

- Проверка `if _, ok := out[k]; !ok { out[k] = []T{} }` — лишняя.
- Ограничение конкретным типом вместо дженерика.
- `K any` вместо `comparable` — не скомпилируется, ключ карты обязан быть сравнимым.

**Развитие.** «Как сохранить порядок групп?» — карта его не хранит; нужен дополнительный слайс ключей в порядке первого появления. «А если групп очень много?» — стоит подумать о потоковой обработке, чтобы не держать всё в памяти.

### Задача 5: разбор и валидация конфигурации `[M]` · ~20 мин

**Условие.** Прочитать конфигурацию из JSON, проверить обязательные поля, подставить значения по умолчанию и вернуть внятную ошибку с указанием проблемного поля.

**На что смотрит интервьюер.**

- Понимает ли, что отсутствующее поле в JSON даёт нулевое значение, а не ошибку.
- Как различает «поле не задано» и «задано нулём» — через указатель.
- Собирает ли все ошибки валидации или падает на первой.
- Возвращает ли ошибку, по которой понятно, что чинить.

**Ключевые фрагменты решения.**

```go
type Config struct {
	Addr    string `json:"addr"`
	Workers *int   `json:"workers"`      // указатель: отличаем 0 от «не задано»
	Debug   bool   `json:"debug"`
}

func (c *Config) Validate() error {
	var errs []error
	if c.Addr == "" {
		errs = append(errs, errors.New("addr: обязательное поле"))
	}
	if c.Workers != nil && *c.Workers <= 0 {
		errs = append(errs, errors.New("workers: должно быть больше нуля"))
	}
	return errors.Join(errs...)
}
```

`errors.Join` возвращает `nil`, если список пуст, поэтому отдельная проверка не нужна. Все нарушения приходят пользователю разом, а не по одному за запуск.

**Типичные ошибки.**

- Валидация «на первой ошибке» — пользователь чинит конфиг по одной строке за раз.
- `Workers int` вместо указателя: ноль неотличим от отсутствия, и умолчание не подставить.
- Сообщение без имени поля: «некорректная конфигурация».
- Валидация при первом использовании вместо старта — сервис падает через час работы.

**Развитие.** «Откуда ещё берут конфигурацию?» — переменные окружения приоритетнее файла, флаги приоритетнее окружения. «Как тестировать?» — таблица случаев: пустой конфиг, частичный, с некорректными значениями.

## Чек-лист перед секцией

- Связка «карта плюс список» для O(1) по двум критериям.
- Реализация `io.Reader` и `io.Writer` как способ встроиться в стандартную библиотеку.
- Повторы с задержкой, отменой и различением видов ошибок.
- Дженерики с `comparable` и функцией-ключом.
- Валидация с накоплением ошибок и указателями для необязательных полей.

Общий приём для middle: **проговаривайте компромиссы**. «Здесь я беру мьютекс на всю структуру — проще и достаточно, при росте нагрузки шардировал бы по ключу» звучит сильнее, чем молча написанный идеальный код.
