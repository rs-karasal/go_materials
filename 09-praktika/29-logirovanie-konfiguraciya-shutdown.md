# 29. Логирование, конфигурация и graceful shutdown

> ⏱ **~50 минут** · теория 20 мин · практика 30 мин

Между «работает на моей машине» и «работает в проде» лежат три вещи: сервис должен настраиваться без пересборки, писать логи, пригодные для машинного разбора, и завершаться, не обрывая запросы на полуслове. Все три задачи закрываются стандартной библиотекой.

## Структурное логирование: `log/slog`

Пакет `log/slog` появился в Go 1.21 и заменил обычный `log` в новых проектах. Разница в том, что запись пишется парами «ключ — значение», а не одной строкой:

```go
logger := slog.New(slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{Level: level}))
slog.SetDefault(logger)

slog.Info("запуск", "addr", cfg.Addr, "debug", cfg.Debug)
```

```json
{"time":"2026-08-16T00:35:27.97+05:00","level":"INFO","msg":"запуск","addr":":8080","debug":true}
```

Почему это важно: строку `fmt.Sprintf("запуск на %s", addr)` систему сбора логов не заставишь отфильтровать по адресу. JSON с полями фильтруется, агрегируется и строит графики.

Четыре уровня — `Debug`, `Info`, `Warn`, `Error`. Порог задаётся при создании, и `Debug`-записи в проде просто не пишутся, не стоя почти ничего.

Обработчиков два: `NewJSONHandler` для прода, `NewTextHandler` для локальной разработки (читается глазами).

**Постоянные поля** прикрепляют через `With`:

```go
reqLog := logger.With("request_id", "abc-123")
reqLog.Info("обработка запроса", "path", "/tasks", "method", "GET")
reqLog.Error("не удалось сохранить", "err", err)
```

```json
{"level":"INFO","msg":"обработка запроса","request_id":"abc-123","path":"/tasks","method":"GET"}
{"level":"ERROR","msg":"не удалось сохранить","request_id":"abc-123","err":"база недоступна"}
```

Идентификатор запроса добавился к обеим записям. Это стандартный приём: middleware из статьи 27 кладёт логгер с `request_id` в контекст запроса, а обработчики достают его — и все записи одного запроса связаны.

Что стоит соблюдать:

- **Сообщение — постоянная строка**, переменные идут в поля. Иначе группировка по сообщению не работает.
- **Ошибку логирует тот, кто её обрабатывает** — правило из статьи 13.
- **Не пишите в логи секреты**: пароли, токены, персональные данные.

## Конфигурация

Стандартный подход для сервисов — переменные окружения: они одинаково работают в контейнере, systemd и на CI, и не хранятся в репозитории.

```go
type Config struct {
	Addr            string
	ShutdownTimeout time.Duration
	Debug           bool
}

func LoadConfig() (Config, error) {
	cfg := Config{Addr: ":8080", ShutdownTimeout: 5 * time.Second}

	if v := os.Getenv("APP_ADDR"); v != "" {
		cfg.Addr = v
	}
	if v := os.Getenv("APP_DEBUG"); v != "" {
		b, err := strconv.ParseBool(v)
		if err != nil {
			return Config{}, fmt.Errorf("APP_DEBUG=%q: %w", v, err)
		}
		cfg.Debug = b
	}
	if cfg.Addr == "" {
		return Config{}, errors.New("пустой адрес")
	}
	return cfg, nil
}
```

Три принципа:

1. **Разумные значения по умолчанию** — сервис должен запускаться без единой переменной.
2. **Проверка при старте, а не при использовании.** Некорректная конфигурация должна ронять процесс сразу, а не через час в первом же запросе.
3. **Вся конфигурация в одной структуре**, собирается в `main` и передаётся явно. Глобальные переменные с настройками делают код нетестируемым.

Для флагов командной строки есть `flag` в стандартной библиотеке; для сложных случаев — `viper` или `envconfig`, которые раскладывают окружение по структуре через теги. Начинать стоит со стандартной библиотеки.

## Graceful shutdown

Когда оркестратор останавливает контейнер, он посылает `SIGTERM` и ждёт. Сервис без обработки сигнала умрёт мгновенно, оборвав запросы в работе — пользователи увидят ошибки на ровном месте.

Корректное завершение состоит из трёх частей.

**Перехват сигнала.** С Go 1.16 это одна строка:

```go
ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
defer stop()
```

Возвращается контекст, который отменяется при получении сигнала, — и дальше работает всё, что вы знаете о контекстах из статьи 21.

**Запуск сервера в горутине** с отдельным каналом для ошибок:

```go
errCh := make(chan error, 1)
go func() {
	if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
		errCh <- err
	}
}()
```

Проверка на `http.ErrServerClosed` обязательна: `ListenAndServe` всегда возвращает ошибку, и при штатной остановке это именно она. Без проверки корректное завершение выглядело бы как сбой.

**Ожидание и остановка:**

```go
select {
case err := <-errCh:
	slog.Error("сервер упал", "err", err)
	os.Exit(1)
case <-ctx.Done():
	slog.Info("получен сигнал, останавливаемся")
}

shutdownCtx, cancel := context.WithTimeout(context.Background(), cfg.ShutdownTimeout)
defer cancel()
if err := srv.Shutdown(shutdownCtx); err != nil {
	slog.Error("некорректное завершение", "err", err)
	os.Exit(1)
}
slog.Info("остановлен корректно")
```

`srv.Shutdown` перестаёт принимать новые соединения и **дожидается завершения текущих запросов** — но не дольше, чем позволит переданный контекст. Таймаут обязателен: без него зависший обработчик задержит остановку навсегда.

Обратите внимание на **новый контекст** для остановки. Использовать отменённый `ctx` нельзя — `Shutdown` завершится мгновенно, не дождавшись ничего.

Полный вывод показывает, что всё сработало:

```json
{"level":"INFO","msg":"получен сигнал, останавливаемся"}
{"level":"INFO","msg":"остановлен корректно"}
```

Не забудьте закрыть остальные ресурсы после сервера: пул базы данных, соединения с очередью, фоновые воркеры. Порядок обратный запуску.

## `main` целиком

Складывая всё вместе, получаем канонический вид точки входа:

1. загрузить и проверить конфигурацию;
2. настроить логгер;
3. открыть зависимости (база, кеш) с проверкой доступности;
4. собрать сервер и маршруты;
5. запустить в горутине;
6. дождаться сигнала;
7. корректно остановиться и закрыть зависимости.

Отдельный приём, который стоит перенять: вынести всё в функцию `run() error`, а в `main` оставить обработку её результата. Тогда `defer` работает нормально — при `os.Exit` отложенные вызовы не выполняются.

```go
func main() {
	if err := run(); err != nil {
		slog.Error("фатальная ошибка", "err", err)
		os.Exit(1)
	}
}
```

## Что запомнить

- `log/slog` пишет структурные логи парами «ключ — значение»; JSON для прода, текст для разработки.
- Сообщение — постоянная строка, переменные идут в поля.
- `logger.With(...)` прикрепляет постоянные поля — так связывают записи одного запроса.
- Конфигурацию читают из окружения, задают умолчания и **проверяют при старте**.
- Вся конфигурация — одна структура, собирается в `main`, передаётся явно.
- `signal.NotifyContext` даёт контекст, отменяемый по `SIGTERM`.
- `ListenAndServe` всегда возвращает ошибку; при штатной остановке это `http.ErrServerClosed`.
- `srv.Shutdown` дожидается текущих запросов — обязательно с отдельным контекстом и таймаутом.
- Логику выносят в `run() error`, потому что `os.Exit` не выполняет `defer`.

## Практика

**1. Структурный лог.** Замените в своём сервисе все `fmt.Println` на `slog` с полями. Настройте JSON в проде и текст при `APP_DEBUG=true`. Готово, когда оба формата работают и уровень переключается.

**2. Связанные записи.** Добавьте middleware, который генерирует идентификатор запроса, кладёт логгер в контекст и логирует начало и конец обработки. Готово, когда все записи одного запроса имеют общий `request_id`.

**3. Конфигурация.** Опишите структуру с пятью параметрами, читайте их из окружения с умолчаниями и валидацией. Проверьте запуск без переменных, с корректными и с некорректными. Готово, когда третий случай даёт понятную ошибку и ненулевой код возврата.

**4. Graceful shutdown.** Реализуйте корректное завершение для сервера с обработчиком, который спит 3 секунды. Отправьте запрос и сразу `SIGTERM`. Готово, когда запрос успел завершиться, а сервер остановился после него.

**5. Таймаут остановки.** Поставьте обработчик со сном 30 секунд и таймаут остановки 2 секунды. Убедитесь, что `Shutdown` вернул ошибку. Готово, когда понимаете, что происходит с недоработавшим запросом.
