# 28. Работа с базой данных: `database/sql`

> ⏱ **~55 минут** · теория 25 мин · практика 30 мин

`database/sql` — не ORM, а тонкая прослойка: вы пишете SQL, пакет управляет пулом соединений и разбирает результаты. Такой подход требует чуть больше кода, зато не прячет от вас запросы. Разберём полный цикл работы со всеми местами, где легко утечь ресурсами.

## Драйвер и подключение

Стандартная библиотека определяет интерфейс, а конкретную базу поддерживает драйвер:

```go
import (
	"database/sql"
	_ "modernc.org/sqlite"
)
```

Подчёркивание — импорт ради побочного эффекта (статья 15): драйвер регистрирует себя в `init()`, напрямую вы к нему не обращаетесь.

Популярные драйверы: `pgx` для PostgreSQL, `go-sql-driver/mysql` для MySQL, `modernc.org/sqlite` для SQLite (чистый Go, без C).

```go
db, err := sql.Open("sqlite", dsn)
```

Здесь главное недоразумение новичков: **`sql.Open` не подключается к базе**. Он только проверяет имя драйвера и готовит пул. Реальное соединение установится при первом запросе — и ошибка подключения вылезет там, а не при старте.

Поэтому проверку делают явно:

```go
ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
defer cancel()
if err := db.PingContext(ctx); err != nil {
	return nil, fmt.Errorf("проверка соединения: %w", err)
}
```

## `*sql.DB` — это пул

Ещё одно недоразумение: `*sql.DB` — не соединение, а **пул соединений**. Он потокобезопасен, создаётся один раз на приложение и живёт до его завершения. Открывать его на каждый запрос — грубая ошибка.

Настройки пула задают явно:

```go
db.SetMaxOpenConns(10)
db.SetMaxIdleConns(5)
db.SetConnMaxLifetime(time.Hour)
```

`SetMaxOpenConns` по умолчанию не ограничен — под нагрузкой приложение способно исчерпать лимит соединений базы. Ставьте разумный предел с оглядкой на `max_connections` сервера. `SetConnMaxLifetime` нужен, чтобы соединения периодически пересоздавались — это спасает при перезапуске базы и работе через балансировщик.

## Запросы

**Изменение** — `ExecContext`:

```go
res, err := s.db.ExecContext(ctx, `INSERT INTO tasks (title) VALUES (?)`, title)
id, err := res.LastInsertId()
```

`Result` даёт `LastInsertId()` и `RowsAffected()` — поддержка зависит от драйвера (в PostgreSQL идентификатор получают через `RETURNING id` и `QueryRow`).

**Одна строка** — `QueryRowContext` со `Scan`:

```go
var t Task
err := s.db.QueryRowContext(ctx, `SELECT id, title, done FROM tasks WHERE id = ?`, id).
	Scan(&t.ID, &t.Title, &t.Done)

if errors.Is(err, sql.ErrNoRows) {
	// строки нет — обычно не ошибка уровня приложения
}
```

`Scan` принимает указатели и раскладывает колонки по переменным в порядке `SELECT`. Отсутствие строки — не паника и не пустой результат, а специальная ошибка `sql.ErrNoRows`, которую проверяют через `errors.Is` (статья 13).

**Много строк** — `QueryContext`:

```go
rows, err := s.db.QueryContext(ctx, `SELECT id, title, done FROM tasks ORDER BY id`)
if err != nil {
	return nil, err
}
defer rows.Close()

var out []Task
for rows.Next() {
	var t Task
	if err := rows.Scan(&t.ID, &t.Title, &t.Done); err != nil {
		return nil, err
	}
	out = append(out, t)
}
if err := rows.Err(); err != nil {
	return nil, err
}
```

Три обязательные вещи, и каждую регулярно забывают:

1. **`defer rows.Close()`** — незакрытые `rows` удерживают соединение, и пул исчерпывается. Симптом: приложение зависает на ровном месте под нагрузкой.
2. **Проверка ошибки внутри `Scan`** — иначе получите нулевые значения вместо данных.
3. **`rows.Err()` после цикла** — `Next()` возвращает `false` и при конце данных, и при ошибке. Без проверки вы примете обрыв за нормальное завершение. Та же логика, что у `bufio.Scanner` из статьи 25.

## Плейсхолдеры и SQL-инъекции

Значения передают **отдельными аргументами**, а не склеивают в строку:

```go
db.QueryRowContext(ctx, `SELECT ... WHERE id = ?`, id)     // правильно

query := "SELECT ... WHERE id = " + userInput               // ❌ инъекция
```

Драйвер передаёт значения отдельно от текста запроса, и подставить SQL через данные невозможно.

Синтаксис плейсхолдера зависит от базы: `?` в MySQL и SQLite, `$1`, `$2` в PostgreSQL.

Единственное, что нельзя параметризовать, — имена таблиц и колонок. Если они приходят извне, сверяйте их с белым списком.

## Транзакции

```go
func (s *Store) MarkAllDone(ctx context.Context) (err error) {
	tx, err := s.db.BeginTx(ctx, nil)
	if err != nil {
		return fmt.Errorf("начало транзакции: %w", err)
	}
	defer func() {
		if err != nil {
			tx.Rollback()
		}
	}()

	if _, err = tx.ExecContext(ctx, `UPDATE tasks SET done = 1`); err != nil {
		return fmt.Errorf("обновление: %w", err)
	}
	return tx.Commit()
}
```

Разберём шаблон — он стандартный.

**`defer` с откатом** гарантирует, что транзакция не останется висеть при раннем возврате или панике. Работает это благодаря именованному результату `err` из статьи 5: отложенная функция видит фактическую ошибку.

**Откат после успешного `Commit` безопасен** — он вернёт `sql.ErrTxDone`, которую здесь можно игнорировать.

**Внутри транзакции работают с `tx`**, а не с `db`. Вызов через `db` уйдёт по другому соединению и в транзакцию не попадёт — ошибка, которую тяжело заметить.

Транзакция держит соединение всё время жизни, поэтому долгих транзакций избегают.

## Подготовленные выражения

`db.PrepareContext` создаёт запрос, разбираемый базой один раз. Выигрыш заметен, когда один и тот же запрос выполняется тысячи раз в цикле. Для обычных сценариев это преждевременная оптимизация: пул и так кеширует подготовленные выражения.

## Слой хранения

Практика, которая себя оправдывает: спрятать SQL за типом с методами.

```go
type Store struct{ db *sql.DB }

func (s *Store) Add(ctx context.Context, title string) (int64, error)
func (s *Store) Get(ctx context.Context, id int64) (Task, error)
func (s *Store) List(ctx context.Context) ([]Task, error)
```

Остальной код работает с задачами, а не с запросами. Для тестов над `Store` объявляют интерфейс — на стороне потребителя, как в статье 11.

## Что вокруг

- **`sqlx`** — тонкая надстройка: раскладывает строки прямо в структуры по тегам, избавляя от длинных `Scan`. Популярный компромисс.
- **`sqlc`** — генерирует типобезопасный Go-код из ваших SQL-файлов. SQL остаётся вашим, код пишется сам.
- **`GORM`** — полноценная ORM. В сообществе Go к ORM относятся прохладнее, чем в Java или Python: они прячут запросы, а Go ценит явность.
- **Миграции** — `goose` или `golang-migrate`. Схему версионируют файлами и накатывают отдельной командой.

## Что запомнить

- Драйвер подключают импортом с `_`; он регистрируется в `init()`.
- `sql.Open` не устанавливает соединение — проверяйте через `PingContext`.
- `*sql.DB` — потокобезопасный пул, создаётся один раз на приложение.
- Ограничивайте пул: `SetMaxOpenConns`, `SetConnMaxLifetime`.
- `ExecContext` — изменения, `QueryRowContext` — одна строка, `QueryContext` — много.
- Отсутствие строки — это `sql.ErrNoRows`, проверяется через `errors.Is`.
- Для `rows` обязательны `defer rows.Close()`, проверка ошибки `Scan` и `rows.Err()` после цикла.
- Значения передают плейсхолдерами; имена таблиц параметризовать нельзя.
- Транзакцию откатывают в `defer` по именованной ошибке; внутри работают с `tx`, а не с `db`.
- Прячьте SQL за типом-хранилищем, интерфейс объявляйте у потребителя.

## Практика

**1. Подключение и схема.** Подключитесь к SQLite, создайте таблицу и убедитесь, что ошибка подключения ловится `PingContext`, а не `sql.Open`. Готово, когда неверный DSN даёт ошибку в ожидаемом месте.

**2. CRUD.** Реализуйте `Store` с методами добавления, чтения по идентификатору, списка и удаления. Готово, когда все четыре работают и отсутствующая запись даёт `sql.ErrNoRows`.

**3. Утечка соединений.** Напишите функцию, которая делает `Query` без `rows.Close()`, вызовите её 100 раз при `SetMaxOpenConns(2)`. Дождитесь зависания, затем добавьте закрытие. Готово, когда обе версии воспроизведены.

**4. Транзакция.** Реализуйте перевод «баллов» между двумя записями: списание и начисление в одной транзакции. Смоделируйте ошибку между операциями и убедитесь, что откат сработал. Готово, когда сумма баллов не изменилась после сбоя.

**5. Инъекция.** Напишите поиск по названию двумя способами: со склейкой строки и с плейсхолдером. Передайте в оба строку `' OR 1=1 --` и сравните результат. Готово, когда видно, что первая версия отдала все записи.
